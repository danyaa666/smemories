# E06_T-090 — Migrate docs fixes, half-applied migration guidance and image-smoke robustness

**Epic:** E06-go-live · **Milestone:** M2 · **Risk:** low · **Priority:** P3 · **Type:** tech-debt
**Depends on:** T-088 (merged) and T-089 (merged; both touch `scripts/image-smoke.sh` and `docs/deploy.md`/`docs/container.md`). Source: the non-blocking findings of the T-088 QA.

#### Description
Five small leftovers of the migration-lock work:
1. **Half-applied migration after a SIGKILL.** A process killed in the middle of a DDL statement leaves a half-applied migration, and the next `smemories-migrate up` fails loudly with "Duplicate column" or "Table already exists". `docs/deploy.md` only says "fix forward", which does not cover this. Write the recovery runbook (how to see which migration is dirty with `status`/`version`, how to inspect and repair by hand, why every migration should be written idempotently where MySQL allows: `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS` is not available in MySQL 8.4 so say what to do instead) and add a reviewer-checklist line. Optionally have `up` print this hint when it fails with those two error numbers (1060, 1050, 1061, 1091).
2. **Silent "ahead" start.** An API started against a schema 1 to 3 migrations ahead starts without any log line. Log one WARN naming both versions (it is the normal state during a rolling deploy, so once at start-up only).
3. **Confusing gap message.** The message for a gap in the middle of the applied versions names the same version twice. Fix the text so it names the missing version and the next applied one.
4. **Wrong exit code in the docs.** `docs/deploy.md` says a bare `down` is refused with exit 4 in prod; it actually exits 2 (only `down --allow-down` in prod exits 4). Fix the doc and add the exit-code table row.
5. **`make image-smoke` can hang and can clash.** It has no timeout on the API run (it hung 20 minutes when another process overwrote the shared `smemories:local` tag). Give the smoke test its own image tag per run (for example `smemories:smoke-<pid>` or the git SHA), a hard timeout on every wait, and clean up the tag at the end; the CI `image` job keeps working.

#### Acceptance criteria
- [ ] AC1 - `docs/deploy.md` has the half-applied-migration runbook and the checklist line; if the failure hint is implemented, a test provokes error 1060 and 1050 and sees it.
- [ ] AC2 - A start against a schema 1-3 ahead logs exactly one WARN naming both versions (test); nothing else about start-up behaviour changes.
- [ ] AC3 - The gap message names two different versions (unit test).
- [ ] AC4 - `docs/deploy.md` exit codes match the code (a test or a script that runs `down` and `down --allow-down` in prod mode and checks 2 and 4).
- [ ] AC5 - `make image-smoke` uses its own tag and a timeout on each wait, still passes in about 25-40 s, and two runs started at the same time do not interfere; CI `image` job green.
- [ ] AC6 - `make lint build test`, `go test -race -tags integration ./...` and `make image-smoke` pass.

#### Added from the T-089 QA (non-blocking)
6. `scripts/image-hygiene.sh no-such-image` prints "ok" and exits 0 because it fails open when the image does not exist. A security gate must fail closed: exit non-zero with a clear message when the image cannot be inspected (CI is safe only because make builds the image first). Add a test for it.
7. A base URL or origin with a query such as `?token=...` is still echoed in the refusal message. Redact query strings as well as userinfo in config error messages.
8. (From the T-021 dev report; do before the first real deploy.) `AccountSuspended` and `SendingPaused` map to `mailer.ErrRejected`, which tells the student "undeliverable address" for what is an account problem the operator must fix. Map them to `ErrUnavailable` (503 `ERROR_MAIL_UNAVAILABLE`, ERROR log with the class, and a distinct `class` label on `smem_mail_send_failures_total` so the T-024 alarm can fire), keep `ErrRejected` for permanent per-address refusals only, and update the mailer conformance test and docs/email.md.
9. (T-021) SES accepts a send to an address on the account-level suppression list and silently drops it (it is not refused), so a student with a hard-bounced address gets no error and no code. Record the result of the sandbox test with `suppressionlist@simulator.amazonses.com` in docs/email.md once the owner has an SES account, and decide then whether the verification screen needs a "change my email" path (a new task, not part of this one).
10. (T-021 QA, before the first deploy) The background mail wait (`svc.Wait()`) is not bounded by SMEM_SHUTDOWN_TIMEOUT: with a hung provider the process needs about 36 s to exit after SIGTERM, over the Fargate 30 s stop timeout, so the task is SIGKILLed. Bound the wait to the remaining shutdown budget (drop and count what is left, `class=shutdown`), and document it in docs/container.md.
11. (T-021 QA, before the first deploy) SES returns `MessageRejected` for an unverified sender identity and for non-verified recipients while the account is in the sandbox. The mailer maps it to `ErrRejected` (class `rejected`), which docs/email.md says not to alarm on, so on day one in the sandbox every sign-up would be rejected silently. Distinguish by the message text/reason where SES gives one (`Email address is not verified`, `Identity ... is not verified` -> class `config` or `sandbox`, mapped to `ErrUnavailable` 503 so it is loud and counted in a metric the T-024 alarm covers); keep `ErrRejected` for per-address permanent refusals; document the sandbox symptom in the email runbook (verify the sender identity first, leave the sandbox, then go live).
12. (T-021 QA, before the first deploy) `resend-verification` refunds the rate-limit try when the provider is down, with no other cap, so an authenticated user can keep hitting SES while it throttles (6 resends in a row went through). Add a separate cap on refunded tries (for example 5 per hour per user) and a test.
