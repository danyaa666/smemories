# E09_T-154 — Web layout runtime: the book draws a layout (Memory Book)

**Epic:** E09-customisation-editor (stage 2) · **Milestone:** M4 · **Risk:** low · **Priority:** P2 · **Type:** feature
**Depends on:** T-153 (the document, the `design.layout` manifest block and `book-data/get` carrying `layout`), T-151 (assets). **Read first:** [ADR 0004](../../../docs/adr/0004-layout-editor.md) (Q1, Q3, Q5 and "Changes this implies" 3, 6), `docs/spikes/editor/src/units.mjs`, `items.jsx`, `book.jsx` (the prototype's `place`, `unplace`, item rendering), the T-143 and T-142 specs and code in `web/src/book/` (`design.tsx`, `env.tsx` `Sheet`, `BookPages.tsx`, `fit.tsx`, `templates/memory.tsx`), `docs/templates.md`, E09 PRD "Stage 2 plan".

#### Why
Before an editor exists the book must be able to draw a layout: print, the preview and the class book all use the same React components. This task adds the layout layer to Memory Book and proves it prints as drawn on A5, A4 and Letter. No editing UI yet.

#### Requirements (SHALL)
1. **Shared geometry** in `web/src/book/layout/geometry.ts`: the stored box type, `place(box, page)` (the draw rule: `left = x·W`, `top = cy·H − h/2`, then clamped inside the page) and `unplace` (its inverse), ported from the spike with tests: round trips on A5, A4, Letter; a box flush to the A5 bottom edge on Letter; clamp at all four edges; rotation about the centre. The editor tasks reuse this module unchanged.
2. **Layer slot.** `Sheet` (`web/src/book/env.tsx`) gets a layer slot inside the page box where the layout draws; the selection chrome of the editor will live outside the page clip (ADR risk 8), so leave a second, empty slot or document where it goes.
3. **Render.** When `data.layout` exists, each page of the book draws, for its page kind: the `bg` (registry asset, the owner's design image through the existing media content route with the `display` variant, or a theme colour token), the `overrides` of the template's editable elements (the template element is positioned absolutely at the placed box, `hidden` hides it; the element keeps its data binding), and the `items` in order: `text` (React text in a `div` with `white-space: pre-wrap`, the manifest's font (`display`/`body` of the active font set), colour token resolved through the active theme, size and alignment, fitted with the existing `FitText`/`fitElement` rule: shrink down to 50 % of the size, then clip, report as the book's fit report does), `asset` (`AssetSvg` with the tint token), `image` (`<img>` with `object-fit`, `radius`, the `print` readiness the book already waits for: the print must wait for every layout image and font before it signals ready). Items never render HTML. Unknown or missing ids (a deleted media id, an asset not in the registry) are skipped without an error.
4. **Notes pages.** The `notes` kind repeats on every notes page: its `bg`, `overrides` (heading only) and `items` appear on each; the flowing notes are untouched.
5. **Manifest.** Correct the proposed `design.layout.page_kinds[].editable` ids in `internal/templates/embed/memory-book.json` (and `docs/templates.md`) to the elements Memory Book can really position; every listed element must get a stable `data-layout-id` attribute (or equivalent prop) in `memory.tsx`; a test pins web ids to the manifest (as T-142/T-143 do). Keep default parity: with no layout the book is byte-for-byte what it prints today (the 163 print-check cases and the DOM snapshots unchanged).
6. **Parity test.** Add to `tools/print-check` the method of ADR 0004 Q5 (editor-independent: print the page with a layout, rasterise at 192 dpi with poppler as print-check already does, compare with the on-screen rendering of the same page): 1-px tolerant difference below 0.5 %, each placed item within 2 px, on A5, A4 and Letter, for a fixture layout with a rotated sticker, a text box (Vietnamese, 500 runes, and a clipped one), an image item, a background and an override, on the cover and on a notes page. Also cover: hidden element, empty layout, a layout with only unknown ids, all four page kinds, and the class book (T-146 path) drawing each student's layout on their own pages.
7. **Performance.** A page with 40 items renders within 10 % of the time of the same page without them in the print-check timing; the layout adds no network request except its images.
8. No new dependency; no API change beyond using the `layout` field of `book-data/get`; the stage 1 customise screen keeps working (the layout layer is independent of themes, fonts and section choices); docs: `docs/templates.md` (how the layout layer is drawn, how a template marks editable elements, the geometry rule) and `docs/e2e.md` if the print-check command list changes.

#### Acceptance criteria
- [ ] AC1 — With the fixture layout the printed PDF shows every item at its placed position on A5, A4 and Letter (parity thresholds met); nothing is cut on any paper size; a missing image or asset is skipped.
- [ ] AC2 — With no layout the book is identical to today (all existing print-check cases and snapshots unchanged).
- [ ] AC3 — Text boxes use the book's fit rule and the active theme and font set; changing the stage 1 theme or font set restyles the text boxes and tinted assets.
- [ ] AC4 — The class book draws each student's layout on their own pages only, within the 8 MiB cap behaviour already tested.
- [ ] AC5 — Lint, typecheck, vitest, i18n parity, `check:api`, build, `make print-check`, `go test ./internal/templates/...`; QA also runs `make e2e` and the class journey.

#### Test plan
QA prints the fixture on all three papers and compares by eye and by the parity numbers, tries hostile layouts (missing ids, huge text, 40 items, overlapping rotated items), switches theme and font set with a layout present, and checks the class book. The ADR's open risk 5 (a real page with photos) is covered here: use a book with photos and notes in the fixture.
