# E09_T-163 — Layout version history and restore (backend)

**Epic:** E09-customisation-editor · **Milestone:** M4 · **Risk:** low (owner-only data, no new personal data, same routes' permission model; touches a migration and concurrency, so QA must run the integration suite) · **Priority:** P2 · **Type:** feature
**Depends on:** none that is open (T-153 and T-156 are merged). **Read first:** `.agents/skills/` backend skills and `docs/api-contract.md`, `docs/db-conventions.md`, `docs/go-conventions.md` (CLAUDE.md "Engineering standards"); `internal/booklayout/*` (handler, service, store, validate, integration_test), migrations `20261101120000_book_layout_tab.sql` and `20261101130000_yearbook_tab_layout_version.sql`, `docs/templates.md` ("Layout block and layout document"), `docs/media.md`, `docs/class-privacy-review.md`, the data export and deletion code that handles `book_layout_tab`.

#### Why
D-43 promised autosave **and version history**: a student who ruins a page at midnight must be able to go back to how it looked before. Autosave overwrites the one stored layout, undo is lost on reload, so a short history of the stored document is the safety net. Retention below is the leader's choice (low risk, recorded in README §4): it is the student's own layout JSON, at most 128 KiB per snapshot, deleted with the book and the account.

#### Retention rule (decided)
Keep at most **30 automatic snapshots** per book, newest first. A snapshot is the document **as it was before** a save that starts a new editing burst: when a `book-layout/save` replaces an existing layout and the newest snapshot of the book is **older than 10 minutes** (or there is none), the replaced document is stored as a snapshot first, in the same transaction as the save. A `book-layout/reset` and a restore also store the replaced document (kind `reset`, `restore`) regardless of age. Beyond 30, the oldest snapshots are deleted in the same transaction. Worst case 30 × 128 KiB = 3.84 MB per book.

#### Requirements (SHALL)
1. **Table** `book_layout_version_tab` (new goose migration, up and down, conventions of `docs/db-conventions.md`: `_tab`, BIGINT ms timestamps, no foreign keys, ULID public ids): `yearbook_id`, `version` (the layout version number the snapshot held when it was replaced, unique with `yearbook_id`), `kind` (`auto`, `reset`, `restore`), `template_id`, `layout_json` (up to 128 KiB), `created_at` (BIGINT ms, the time of the replacement). Index `(yearbook_id, created_at DESC)`.
2. **Snapshots on save, reset and restore** as in the retention rule, **atomically** with the write that replaces the document (one transaction; a failed snapshot fails the save with the usual 500, never a silent loss). The check "newest snapshot older than 10 minutes" and the insert must be race-free with two concurrent saves (conditional statement or row lock on the book's layout row): two parallel saves never produce two snapshots within the window, and never none. The prune happens in the same transaction.
3. **Routes** in the `book-layout` namespace, owner only (404 for anyone else, also for a missing book), `{status,data}` envelope, rate limit shared with the save limits: `POST /api/book-layout/version-list` (`yearbook_id`; returns up to 30 `{id, version, kind, created_at, item_count, bytes}` newest first, no layout bodies), `POST /api/book-layout/version-get` (`yearbook_id`, `id`; returns `{id, version, kind, created_at, layout}`), `POST /api/book-layout/restore` (`yearbook_id`, `id`, `base_version`). Ids are public ULIDs, never the numeric key.
4. **Restore semantics**: the snapshot document is re-validated like a save against the book's **current** template manifest, the asset registry and the owner's **current** design images. Items that point to an asset id that no longer exists or to a design image that was deleted are **dropped** (and so is a missing background), and the answer carries `dropped: <count>`; any other problem (unknown key, over a limit) is `ERROR_INVALID_LAYOUT` with the problem list as for save. Restore needs `base_version` equal to the current version (`ERROR_VERSION_CONFLICT` with the stored document otherwise, as for save), stores the replaced document as a `restore` snapshot, writes the restored document as a **new** version (the counter of T-156 only goes up) and answers `{version, layout, dropped}` like `save`. A snapshot taken under another template than the book's current one cannot be restored (`ERROR_VERSION_TEMPLATE_CHANGED`, 409 or the repo's convention, documented); in practice a template change already deletes the history (requirement 5).
5. **Deletion**: changing the book's template (which deletes the layout) deletes its snapshots; deleting the yearbook and deleting the account delete them (same code paths and tests as `book_layout_tab`); `book-layout/reset` keeps them (it stores one more). The data export lists the number of snapshots per book (not their bodies) wherever it lists the layout; update the export doc and test.
6. **Privacy**: snapshots are never readable by anyone but the owner. A class admin's read path (D-36) does **not** include versions; the class matrix test asserts 404 for admin, member, other-class admin and anonymous on all three new routes. `docs/class-permissions.md` and `docs/class-privacy-review.md` list the new table.
7. **Observability**: counters for snapshots written (label `kind`), pruned and restores (labels: ok, conflict, invalid, template_changed); no layout content or ids in logs; one slog line per restore with the book's public id, version numbers and `dropped`.
8. **Tests**: validation and store unit tests; integration tests (real MySQL) for the retention rule (the 10-minute boundary using an injectable clock, 31st snapshot prunes the oldest, reset and restore snapshots regardless of age), the race (two concurrent saves, `-race`), restore with a deleted design image (dropped count) and an asset id removed from the registry, restore conflict, cross-book and cross-user access (404), deletion paths (template change, yearbook delete, account delete) and the export count; a migration up/down test as the repo does for others; the class matrix. Newman/Postman collection steps for the three routes in the repo's API collection (the stale-assertion lesson of T-155: assertions must match the real envelope).
9. **Docs**: `docs/api-contract.md` (three routes, the `dropped` field, the retention rule), `docs/templates.md` (history paragraph), OpenAPI/`web/src/api/schema.d.ts` regenerated if the repo generates it (`make` target, keep `check:api` green), README "Data we keep" or the privacy docs where retention is listed.

#### Acceptance criteria
- [ ] AC1 — Saves in one editing burst (several saves within 10 minutes) produce one snapshot; a save after a 10-minute gap produces one more; 31 gaps keep the newest 30; verified by the integration test with an injectable clock and by QA with a real database.
- [ ] AC2 — Restore brings back the earlier document as a new, higher version, with items whose design image or asset is gone dropped and counted; restore with a stale `base_version` is a conflict and changes nothing.
- [ ] AC3 — The three routes answer 404 for anyone but the owner (matrix incl. class admin); the snapshots are deleted with template change, yearbook and account; the export reports the count.
- [ ] AC4 — Two concurrent saves never lose the snapshot or duplicate it (`go test -race`, repeated 20 times in the integration package).
- [ ] AC5 — `make lint test` and `make test-integration` (default DSN), `make migrate` up and down, `check:api`, the Postman/newman run green; QA writes the integration result lines (counts, head SHA) in the board comment.

#### Test plan
Dev: the tests of requirement 8 on a private compose stack. QA: runs the full integration suite and the newman collection on the PR head, fills a book with 40 saves spread over time (clock control or direct DB timestamps), restores several, deletes a design image and restores a version that used it, restores with two tabs racing (one conflict), checks the three deletion paths and the export, and checks that the response sizes stay small for `version-list` (no bodies).
