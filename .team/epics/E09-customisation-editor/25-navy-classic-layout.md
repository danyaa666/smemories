# E09_T-166 — Navy Classic: page kinds and editable elements for the layout editor (web + manifest)

**Epic:** E09-customisation-editor · **Milestone:** M4 · **Risk:** low · **Priority:** P2 · **Type:** feature
**Depends on:** T-154 (layout runtime; merged) and T-162 (the palette; merged). Independent of T-164/T-165 (no shared files except i18n and docs: rebase if one merges first). **Read first:** `web/src/book/templates/navy.tsx` + `navy.css`, `internal/templates/embed/navy-classic.json`, the Memory Book precedent: `internal/templates/embed/memory-book.json` (`design.layout`), `memory.tsx` (`<Editable layoutId=...>`, `useLayoutBg`), `web/src/book/layout/runtime.tsx`, `docs/templates.md` ("Layout block and layout document"), the T-154 spec 13 and the T-153 validation (`internal/booklayout/validate.go`: how a template's `design.layout` is checked), `docs/e2e.md`.

#### Why
D-39/D-41 and D-42 name two pilot templates. Today only Memory Book has a `design.layout` block, so a student with Navy Classic gets the stage 1 customise screen but no free-layout editor (the editor opens with nothing to place). Navy Classic is the formal template (gold frame, navy and cream pages, serif letter); it must be editable without losing its look.

#### Requirements (SHALL)
1. **Manifest**: add `design.layout` to `navy-classic.json` in the shape of Memory Book's: `page_kinds` `cover`, `profile`, `notes` (`repeats: true`) and `back`, each with the `editable` element ids; `text_fonts` (the font sets' roles that exist in Navy Classic, from `navy.css`/`design.tsx`), `colors` (the theme tokens Navy defines: navy, gold, cream, ink and the theme accents; do not invent tokens the CSS lacks), `text_size` {min 8, max 96}, `safe_margin_mm` (as drawn by the frame; the gold `Frame` may be wider than 5 mm: pick the value that keeps added items inside the frame's inner rule and document it). The final list of editable ids is **the dev's call after reading `navy.tsx`**, with this guidance, and it goes in the PR description with the reason for each omission: cover: school line, the "class of / year" block, the title, the motto, the class name; profile: the heading/eyebrow and the oval portrait (not the letter paragraphs, which flow by content); notes: the heading/eyebrow (not the autographs); back: the thanks text and the footer group. Ids are `<kind>.<name>` like Memory Book's.
2. **Runtime**: wrap each listed element in `navy.tsx` with the same `<Editable layoutId=...>` used by `memory.tsx` (same behaviour: moved elements are drawn through the page-anchored portal with `place`, `hidden` hides, data binding kept, **no change to the default output**). The gold `Frame`, the dividers and the cap ornament are decoration and stay fixed unless the dev finds one that is trivially safe to expose; say which. A moved element keeps its own font fit rule (`FitText` keys stay unique per element).
3. **Background**: the `bg` of a page kind replaces the `Page tone` fill (navy or cream) behind the frame; the frame and text stay on top. A theme colour token that is not legible with the page's text colours is the student's choice (no automatic contrast rewrite), but the editor's contrast hint from T-159/T-162 (if present) must work with Navy's tokens; if none exists, nothing new here.
4. **Parity**: with no layout the Navy Classic book is byte-for-byte what it prints today (all existing print-check cases and DOM snapshots unchanged). With the fixture layout (a moved and rotated cover title, a hidden motto, an added sticker, an added text box in Vietnamese, an image item, a background on each page kind) the print route draws what the editor shows within the T-154 thresholds (1-px tolerant difference below 0.5 %, each placed item within 2 px) on A5, A4 and Letter, cover/profile/notes/back, with photos and several notes in the fixture.
5. **Server validation** needs no code change if T-153 validates against the manifest; verify it: a layout with Navy ids saves, an id of Memory Book on a Navy book is rejected `ERROR_INVALID_LAYOUT`, and changing the template to the other one deletes the layout as today (add the integration test cases; do not touch the migration or the table).
6. **Editor**: the same editor (T-159..T-162) works on Navy Classic unchanged: the page strip shows its four kinds, the property panel lists its fonts and colours, the palette tints with its tokens. Fix what breaks (hard-coded Memory Book assumptions such as page sizes, class names or colour names are bugs to remove, not to special-case).
7. **Tests**: manifest-to-web id pin test (as for Memory Book: every manifest id has a marked element and the reverse); unit tests for the new `Editable` wrappers where Memory Book has them; the integration cases of requirement 5; Playwright spec `tools/e2e/editor-navy.spec.mjs` (switch a test book to Navy Classic, open the editor, move the cover title, hide the motto, add a sticker and a Vietnamese text, set a background, reload and see the same, open the print route and compare to the editor; template switch to Memory Book clears the layout) plus the print-check parity fixture; the existing Memory Book e2e stays green.
8. **Docs**: `docs/templates.md` (Navy Classic's page kinds, editable ids, safe margin and what stays fixed and why); the stage 2 section of the PRD is updated by the leader, not in the PR.
9. No new dependency; nothing under `.team/`; no change to the Go renderer or API.

#### Acceptance criteria
- [ ] AC1 — On a Navy Classic book a student moves/rotates/hides listed cover and profile elements, adds a sticker, a Vietnamese text box and an own image, sets a background per page kind, reloads and sees the same; the printed `/book` matches (parity thresholds met on A5, A4, Letter).
- [ ] AC2 — With no layout the Navy Classic print is unchanged (print-check and snapshots green); the Memory Book editor and print are unchanged.
- [ ] AC3 — Server: Navy ids accepted, Memory Book ids on a Navy book rejected, template switch clears the layout; all in integration tests.
- [ ] AC4 — The editable list in the PR names every element and every omission with a reason; the notes pages' autographs and the profile letter paragraphs stay content-flowed.
- [ ] AC5 — Lint, prettier, tsc, vitest, `lint:i18n`, `check:api`, build, `go test ./internal/templates/... ./internal/booklayout/...`, `make test-integration` for touched packages, the e2e suite (incl. `editor-navy.spec.mjs`) and `make print-check` green.

#### Test plan
Dev: requirement 7 on a private compose stack (non-default ports; `scripts/e2e.sh` directly). QA: runs everything on the PR head, prints a Navy book with a heavy layout on all three papers and compares to the editor by eye and by the parity numbers, tries hostile moves (title dragged over the frame, 40 items, rotated sticker across the frame), switches theme and font set with a layout present, switches the template back and forth, and checks the class book still draws Navy members without layouts.
