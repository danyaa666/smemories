# E09_T-169 — Spike: Doory-template import and a Fabric.js image studio beside the DOM editor — integration reliability, ADR 0005

**Epic:** E09-customisation-editor · **Milestone:** M4 · **Risk:** low (spike: no product code, no dependency added to `web/`) · **Priority:** P1 · **Type:** spike
**Depends on:** none. **Owner decision:** D-45 (2026-11-04). **Read first:** `docs/adr/0004-layout-editor.md` (the DOM editor stays the page editor; its numbers are the bar), `docs/adr/0003-html-print-export.md`, `docs/templates.md` ("Layout block and layout document"), `internal/booklayout/validate.go` (the one validator every layout passes), `docs/assets.md` (asset registry, licence files), `docs/media.md` (design-image upload pipeline), `docs/spikes/editor/` (how the last spike was kept and run), `docs/e2e.md` (private stacks, ports).

#### Decision this spike serves (D-45, owner, 2026-11-04)
The owner chose the **hybrid**: the DOM editor stays the editor for pages (D-43 stays for pages: print parity, Vietnamese typing, live book data). **Fabric.js (MIT) is allowed, isolated**, as an image studio for graphics, and **templates from Doory** (https://github.com/shaongitbd/doory, a Fabric.js design editor) are to be usable in our system. The owner's stress: **reliability of the integration**. Three product features follow after this spike: a template chosen per section (cover, profile, notes, back); "save my edited page as my own template"; editing a page or the whole book page by page, with save, print and a return to the book manage page. What this spike must establish is **how to bring templates in and run the studio so that neither can corrupt a student's book or break printing**.

Leader's working design (the spike confirms or corrects it with evidence):
- **Doory is a template source and a UX reference, not a runtime dependency.** A build-time tool converts a Doory design (Fabric JSON) into **our layout document** (T-153 model: boxes in page-width thousandths, `text`/`asset`/`image` items, `bg`) and the result is committed to our repo as our own files with licence files. Nothing from Doory runs in production: no Django, no Doory frontend, no live fetch.
- **Every template, imported or saved by a student, passes the same server validation as a layout save** (T-153), in CI for shipped ones (a template that fails the validator fails the build) and at save/apply time for students' own. A bad template therefore cannot reach a book.
- **Text stays real text in the DOM editor** (Vietnamese typing, 500 code points, fit rule, print); a Doory text object becomes our text item, never pixels.
- **The Fabric.js studio produces images only** (PNG/JPEG/WebP through the existing design-image upload; no user SVG) and is flattened on save, never re-opened as a shared document of the page. It is lazy-loaded, behind an error boundary and a feature flag, so a studio failure cannot touch the book or its autosave.

Facts the leader found on 2026-11-04 (verify, do not trust): Doory created 2026-10-10, ~2.0k stars, 276 commits on `main`, no GitHub releases (tags v0.1.0, v0.2.0), 10 starter templates, multi-page designs of different sizes, Fabric.js + React 19 + Zustand + Yjs frontend, Django 5 + PostgreSQL backend, export with jsPDF; licence **Attribution Assurance License** (GitHub: NOASSERTION): redistributing the program requires showing the credit "Doory by Siam, creator and maintainer of Doory, https://github.com/shaongitbd/doory" when it starts (web app: on its pages) and keeping the GPG-signed licence text and NOTICE. Its README does not mention Vietnamese or IME.

#### Questions to answer (each with a measurement or an experiment)
1. **Template inventory and conversion coverage.** At a pinned Doory commit, document the design/template JSON format (pages, sizes, object types, fonts, assets, groups, masks, effects). Build the converter prototype Fabric-JSON → our layout document for the four page kinds. For **every object in all 10 starter templates** record: converts exactly / converts approximately (say how) / cannot convert (dropped, or flattened into a design image). Report coverage by object count and by template, and show the 3 best and 3 worst as before/after renders on A5, A4 and Letter. Define the policy for: page-size mismatch (Doory canvases such as 1080 x 1080 or posters against our A5/A4/Letter ratios: fit, crop or letterbox), fonts (map to our Vietnamese-capable OFL families, fallback plus warning), images (never hotlinked: copied into our asset registry or design-image store with a licence file, or dropped), text (500-code-point cap, plain text, fit), groups, rotation, opacity, shadows, gradients, masks and curved text (we do not have all of these: approximate, flatten or refuse, per item type).
2. **Round trip and determinism.** The converter is a deterministic pure function with a report (what was converted, dropped, approximated). Prove: the same input gives byte-identical output; the output passes `internal/booklayout` validation for each page kind; the converted page prints with parity to the editor view (ADR 0004 Q5 method: pixel difference at 192 dpi, items within 2 px) for at least three converted templates.
3. **Where templates live and how a student uses them.** Propose the storage and apply model for: shipped templates (files in the repo, like the template manifests), a student's **own saved templates** (a table, owner only, size/count limits, deleted with the account) and **per-section template choice** (cover, profile, notes, back). Apply = copy the template's layout into the book's layout for that page kind (one version-history snapshot, T-163 rules; items whose asset/image is gone are dropped and counted, as restore does). State what a template may contain (only what the layout validator allows) and what it must not (no user SVG, no external URLs, no scripts, no ids of other users' media). Compare with two alternatives (templates as separate book-level templates; layout presets inside one template) and say why the chosen one is the most reliable.
4. **Studio integration reliability.** Define and test the failure modes: studio chunk fails to load; studio crashes mid-edit; export too large or out of memory on a phone/tablet; upload fails, is rate limited (429), quota exceeded or the 30-image cap (T-164 `ERROR_DESIGN_IMAGE_LIMIT`); double click sends two uploads; the student leaves with unsaved studio work; Fabric.js version bump changes behaviour. For each, state the expected outcome ("the book is untouched", "the draft is kept in the browser", "one clear message") and prove it for the main ones with a prototype or a test. Decide: flatten resolution per paper size (A5 at 300 dpi is about 1748 x 2480 px) and pixel/memory caps, output format, transparency, whether the studio's working document is kept (recommendation expected: not stored on the server; at most a local draft), keyboard alternatives for essential operations, and whether any text tool is allowed (recommendation expected: none, text stays in the DOM editor; if the owner wants text in the studio, measure Telex/VNI there with CDP `Input.imeSetComposition` as `docs/spikes/editor` did, plus an owner checklist).
5. **Which jobs justify the studio at all.** For each concrete job (photo crop and filters, collage, cut-out sticker, doodle, shapes with effects, curved text) say whether CSS/SVG, the existing image `fit`/radius controls, a vector "draw" item stored in the layout, or a tiny MIT helper already does it with less weight and no raster. Recommend the **smallest first studio** (possibly none for the first release, with the template import going first).
6. **Licence and obligations (information for the owner, not legal advice).** Read `LICENSE`, `NOTICE`, `THIRD_PARTY.md`, `licenses/` at the pinned commit. For the **templates and their assets** (images, fonts, models): what licence each carries and whether it may ship in a commercial product; whether using only Doory's data format and templates, with none of its code, triggers the Attribution Assurance credit, and where the credit would have to appear if it does; Fabric.js MIT notice. If anything is unclear the plan is to **recreate the templates ourselves in our format, using Doory's only as inspiration**, and the ADR says which templates that applies to. List every obligation with the quoted source file.
7. **Dependency and supply-chain health.** Fabric.js version to pin and its release cadence; `npm audit` on the studio prototype; bundle cost (gzip) of the lazy studio chunk and proof it is absent from the main and print bundles; Doory's health only as far as it matters for a one-time import (one maintainer? license stability?), and the rule that no future Doory release can affect production (we hold our converted files).
8. **Recommendation and task plan.** One recommendation, with the numbers, and the **task list that replaces the rest of the stage 2 plan**: template model and storage, the converter tool and shipped templates, the template gallery and apply UI (per section), "save my page as a template", the page-by-page editing flow with save/print/return to the book manage page, the studio (if question 5 justifies it), plus tests, security review and docs. Mark which tasks need an owner decision (the attribution line if required, any new dependency beyond Fabric.js, paid assets).

#### Requirements (SHALL)
1. Write `docs/adr/0005-doory-templates-and-fabric-studio.md` (status "proposed" until the leader accepts it and the owner confirms the open licence points) with the answers, numbers, tables, the recommendation and the task plan.
2. Prototypes, the converter and sample converted templates live in `docs/spikes/canvas/` with their own `package.json` and a `README.md` that reproduces every number from a clean checkout. **Do not vendor Doory's source**: the README clones it at a pinned commit SHA into a git-ignored folder (add the folder to `.gitignore` in the same PR). 5. Time-box: at most 3 dev wake-ups. If time runs short the order of priority is: 1, 2, 6, 3, 4, 5, 7, 8.
