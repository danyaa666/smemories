# E09_T-169 — Spike: canvas foundation (Doory / Fabric.js) against our DOM editor, ADR 0005

**Epic:** E09-customisation-editor · **Milestone:** M4 · **Risk:** low (spike: no product code, no dependency in `web/`) · **Priority:** P1 · **Type:** spike
**Depends on:** none. **Read first:** `docs/adr/0004-layout-editor.md` (the DOM decision and its measurements: the new ADR must beat or match them on the same criteria), `docs/adr/0003-html-print-export.md`, `docs/templates.md`, `docs/spikes/editor/` (how the last spike was kept and run), `docs/e2e.md` (private stacks, ports), owner decision D-43(a) ("no canvas library, no paid SDK"), E09 PRD "Stage 2 plan".

#### Why
On 2026-11-04 the owner asked to "integrate canvas editing using an open-source project", pointing at **Doory** (https://github.com/shaongitbd/doory, "open source Canva alternative"), and for three product features: a template chosen **per section** (cover, profile, notes, back), **save my edited page as my own template**, and editing a page or the whole book page by page with save, print and a return to the book manage page. That reopens D-43(a). The leader does not decide a foundation by opinion: this spike measures it, the way T-150 measured the DOM editor, so the owner decides on numbers. Until the owner decides, T-165..T-168 continue (they stand on the DOM editor) and the three new features are **not** specified, because their data model depends on the answer.

Facts the leader found on 2026-11-04 (verify them, do not trust them): Doory was created 2026-10-10, ~2.0k stars, 276 commits on `main`, no GitHub releases (tags v0.1.0, v0.2.0), pushed 2026-11-02. Stack: **Fabric.js** canvas, React 19, TypeScript, Vite, Zustand, Yjs for co-editing; backend **Django 5 + DRF + Channels + PostgreSQL** (Redis and S3 optional), Docker Compose with nginx; 10 starter templates; multi-page designs; export PNG/JPG/SVG/PDF (jsPDF) with bleed and crop marks; MCP server for AI; ONNX Runtime Web in the bundle. Licence: **Attribution Assurance License** (GitHub shows NOASSERTION): redistribution (including the program run for users) requires showing, each time the program starts and, for a web app, on its pages, the credit "Doory by Siam, creator and maintainer of Doory, https://github.com/shaongitbd/doory", and keeping the GPG-signed licence text and NOTICE. Its README does not mention Vietnamese or IME.

#### Options to compare (all five, same criteria)
- **A. Keep the DOM editor** (ADR 0004) and add the new features on it. The baseline: use ADR 0004's own numbers.
- **B. Fabric.js (MIT) inside our own editor**: replace the DOM editor's interaction layer with a Fabric canvas per page; our own UI, our Go API, our print path.
- **C. Doory's frontend embedded/forked into our web app**, backed by our Go API instead of Django (list exactly which Django endpoints, WebSocket channels and storage the frontend needs and what replacing them costs).
- **D. Doory run as a separate self-hosted service** (Django, PostgreSQL, Redis, Channels) next to our stack, with pages going in and out as JSON/PDF/PNG.

- **E. Hybrid: keep the DOM editor for pages and use Fabric.js only as an isolated, lazy-loaded "image studio"** (owner idea 2026-11-04). The studio edits graphics (for example crop and filters of a photo, a collage, a cut-out sticker, a doodle) and its output goes back through the existing design-image upload (`media` purpose=design: re-encoded, metadata stripped, quotas) to be placed by the DOM editor as an ordinary image item. Text stays in the DOM editor (Vietnamese typing, print, data binding). For E answer: which concrete needs justify a canvas at all (list each, and for each whether CSS/SVG, the existing image `fit`/radius controls or a tiny MIT drawing helper already do it with less weight); the resolution the studio must export for print (A5 at 300 dpi is about 1748 x 2480 px) and the memory cost on a phone; the bundle cost of loading Fabric only on that screen; that no user SVG is accepted (PNG/JPEG/WebP only); and the rule for two editors never editing the same object (flatten on save, no round trip back into Fabric).

#### Questions to answer (each with a measurement or an experiment)
1. **The book is data-bound and flows.** Our pages show profile fields, photos and notes that come from the database and flow across pages (notes). Can a canvas page express cover/profile/back with live bindings (text taken from a field id, image from a photo id) and what does it do with the notes pages, which flow by content? Build the Memory Book cover and profile as a canvas page in each applicable option and say what is lost or needs a new mechanism.
2. **Vietnamese input.** Telex and VNI composition in the text boxes of B and C/D (Playwright Chromium with CDP `Input.imeSetComposition`, the method of `docs/spikes/editor`; also Firefox and WebKit engines if available): "Việt Nam", "đường", "Tiếng Việt có dấu", at 499/500 code points, paste as plain text, caret after composition. Report letters lost or doubled. Add a short manual-check list for the owner's Mac (as T-161 did).
3. **Print parity and fonts.** The book prints by the browser from HTML (ADR 0003, A5/A4/Letter, the 163+ print-check cases). For B/C/D: how does a canvas page reach the printed PDF (rasterised canvas? SVG export? jsPDF?), at what quality at 192 dpi, with our Vietnamese-capable OFL fonts, bleed, and text that stays real text (searchable, sharp). Measure the pixel difference of a fixture page against the editor view, as ADR 0004 Q5 did, and the PDF size. A rasterised page is a failing answer unless the owner accepts it: say so plainly.
4. **Templates and the three new features.** How Doory stores a design/template (JSON shape, size limits, assets); how "template per section", "save my edited page as my own template" and "page by page across the whole book" would map in each option; what happens to the existing layout documents (T-153, `book_layout_tab`), version history (T-163/T-165) and the class book (T-167) if we change foundation. Give a migration sketch and a task-count/size estimate per option, in the same units as the 17 stage 2 tasks.
5. **Integration and operations (C/D).** Auth bridging with our sessions, file uploads and quotas (our media pipeline T-009/T-152 strips metadata and re-encodes: does Doory's upload path go around it?), SVG/XSS and template-injection exposure, multi-tenant isolation, SSRF, rate limits, Yjs/Channels WebSocket load and cost, extra services (Django, PostgreSQL, Redis) next to Go/MySQL/Valkey on the planned AWS deploy, backups, observability. Run `npm audit` and `pip-audit` (or the repo's lockfile scanners) on the pinned commit and report counts by severity.
6. **Licence and obligations.** Read `LICENSE`, `NOTICE`, `THIRD_PARTY.md`, `licenses/`. List what the product must show and keep (the start-up credit on our pages, the signed licence text), whether the attribution can sit on an "about" page or must be on the editor/page screens as the NOTICE says, bundled components with their own obligations (fonts, ONNX models and WebAssembly, any non-commercial model weights), and whether every asset and font in the pinned commit is allowed in a commercial product. This is information for the owner, not legal advice; flag anything unclear as an open question.
7. **Project health and effort.** Age, commit rate, issues and PRs, bus factor (one maintainer?), test coverage, tags, how often the API/JSON schema changed between v0.1.0 and v0.2.0 (breaking-change rate), CVE history. If we fork, what do we maintain? Performance: 100 objects on a page at 4x CPU throttle in Chrome (frame time while dragging), bundle size (gzip) of the editor route, accessibility (keyboard move/resize, labels, screen reader), phone behaviour at 375 px.
8. **Recommendation.** A table of A/B/C/D against questions 1..7 with the numbers, then one recommendation with the reasons, the cost of being wrong, a rollback path, and — if the answer is not A — the task list that would replace the remaining stage 2 plan. State the owner decisions it needs (foundation, the attribution line, any new service and its cost).

#### Requirements (SHALL)
1. Write `docs/adr/0005-canvas-foundation.md` (status "proposed" until the owner decides) with the answers, numbers, the comparison table (A to E) and the recommendation. Link the evidence files.
2. Prototypes and scripts live in `docs/spikes/canvas/` with their own `package.json` and a `README.md` that reproduces every number from a clean checkout. **Do not vendor Doory's source** into our repository: the README clones it at a pinned commit SHA into a git-ignored folder (add the folder to `.gitignore` in the same PR). Nothing in `web/`, `internal/`, `cmd/`, CI or dependencies of the product changes.
3. Run Doory's stack (options C/D) only on a private compose project with its own name and non-default ports; never touch the main project's volumes, never restart Docker Desktop, never kill processes you did not start. The stack is torn down at the end; the README says how to bring it up again. No secrets from `.env` are read or committed (use Doory's `.env.example` with throw-away values).
4. If a candidate fails a question (for example Vietnamese composition loses letters, or printing is rasterised), say so plainly with the evidence; do not hide it. If a question cannot be answered in the time-box, report what is missing instead of guessing.
5. Time-box: at most 3 dev wake-ups. Priority of questions if time runs short: 2, 3, 1, 6, 4, 5, 7.
