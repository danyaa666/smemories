# E09_T-179 — Stage 2 hardening: fuzz the layout parsers, storage budget per user, abuse limits, no content in logs

**Epic:** E09-customisation-editor · **Milestone:** M4 · **Risk:** low (tests, docs and small guards; any guard that changes behaviour is listed in the PR) · **Priority:** P2 · **Type:** test (security)
**Depends on:** T-173 (merged; the template routes exist). **Read first:** `internal/booklayout/` (`validate.go`, `service.go`, `versions.go`, `ownpage.go`, `pagetemplate.go`, handlers), `internal/textx`, `docs/templates.md`, `docs/api-contract.md` (limits), `docs/class-privacy-review.md`, `docs/observability.md`, `docs/db-conventions.md`, the rate-limit code the layout routes use (`s.take`), `docs/security*.md` if present, T-153/T-163/T-172/T-173 specs.

#### Why
Stage 2 added a user-supplied JSON document (128 KiB per book), 30 history snapshots per book, 20 own templates per user and five write routes that parse and re-validate it. Each is an untrusted-input parser and a growth path. Before the editor is offered to every student the team must know the worst case on disk and in CPU, and prove that hostile input fails safely.

#### Requirements (SHALL)
1. **Fuzzing**: Go native fuzz targets (`func FuzzX(f *testing.F)`) for `Validate`, `ValidateRestore`, the page `strip`, `withPage`, the layout/page JSON decode path of `apply-template`/`template-create`/`save`, and `textx.Clean` for names; seeds from the existing fixtures and from QA's hostile cases (deep nesting, huge numbers, NaN-looking strings, lone surrogates, NUL and bidi control characters, duplicated keys, 10 000 items, 1 MB strings). `go test` (no `-fuzz`) runs the seeds in CI. Run each target with `-fuzztime=5m` locally (record the result lines); every crash, panic, hang over 1 s or non-idempotent normalisation found is fixed with a regression seed committed under `testdata/fuzz/`. Properties to assert: never panics; accepted documents re-validate to the same bytes (idempotent); accepted documents never exceed the size limits; rejected input never partially writes (store-level test with a fake or MySQL).
2. **Complexity limits**: the JSON decode of a layout, page or template rejects nesting deeper than a fixed limit (say 16) and bodies over the route's limit **before** unmarshalling into maps; show with a test that a 2 MB body, a 100 000-level nested array and 200 000 tiny items fail fast (under 200 ms) with `ERROR_TOO_LARGE`/`ERROR_INVALID_LAYOUT`, and that allocation is bounded (a `testing.AllocsPerRun` or `runtime.MemStats` delta check with a stated ceiling).
3. **Storage budget**: write `docs/layout-storage-budget.md` with the worst case per book and per user (current layout 128 KiB + at most 30 snapshots x 128 KiB per book + own templates 20 x 64 KiB; multiply by the number of books a user can have today: read the code for the real cap, and if there is none say so), the same figures after JSON/MySQL overhead measured on a real table (insert maximal rows, read `information_schema` sizes), a cost estimate per 1 000 students at the worst case and at a typical case (the leader supplies typical = 5 saves a week, 3 KiB layouts; state it), and the SQL an operator runs to see the biggest users. If the worst case per user is larger than 30 MB, recommend a cap (books per user, or a total bytes cap on snapshots) and **ask the leader** in a board comment; do not change behaviour without that answer.
4. **Rate limits and body caps**: a table in the doc and a test per route of the `book-layout` namespace (`get`, `save`, `reset`, `version-list|get`, `restore`, `template-list|create|delete`, `apply-template`): which limit it takes, that the limit is per user, that a limited call answers 429 with `Retry-After`, that an anonymous call is 401 before any parsing, and that the request-body cap is enforced before decoding. Gaps found become fixes in this task if small, otherwise board comments.
5. **No content in logs, metrics or errors**: a permanent Go integration test that runs create, apply, save, restore and a failing apply with a sentinel string inside text items, names and image ids, captures the application log output and the Prometheus text output (the T-173 QA probe did this by hand), and fails if the sentinel appears in either; also in the `ERROR_INVALID_LAYOUT` problem list (paths and codes only).
6. **Text safety**: confirm and test that text items and names cannot carry control characters (NUL, U+202E and other bidi overrides in names, lone surrogates), that normalisation is NFC where the editor expects it (Vietnamese composed/decomposed input from macOS Telex gives the same stored form and the same code-point count as the limit uses), and that the web renders layout text only as text (no `dangerouslySetInnerHTML`; grep as a test or a lint rule for the `web/src/book` tree).
7. **Threat model note**: `docs/stage2-threat-model.md` (one page): assets (student text and images, the layout document, history, own templates), trust boundaries (student, class admin, other student), the abuse cases above with the control that stops each and the test that proves it, and what is deliberately not covered (denial of service by many accounts: left to the global rate limiting and the deploy layer).
8. No new dependency; nothing under `.team/`; behaviour changes only for limits found missing, each listed.

#### Acceptance criteria
- [ ] AC1 — Fuzz targets exist for every function of requirement 1, the seeds run in `go test`, and each target ran at least 5 minutes with no crash (lines in the PR); any finding has a committed regression seed and a fix.
- [ ] AC2 — The 2 MB, 100 000-level and 200 000-item inputs fail within 200 ms with the right code and bounded allocation.
- [ ] AC3 — `docs/layout-storage-budget.md` has measured numbers for a maximal book and a maximal user and the operator query; a cap recommendation is on the board if the worst case per user exceeds 30 MB.
- [ ] AC4 — Every layout route has a rate-limit and body-cap test; the sentinel test proves no layout content in logs, metrics or problem lists.
- [ ] AC5 — Text-safety tests pass for control characters and Vietnamese composed/decomposed forms; the threat model note is committed.
- [ ] AC6 — Lint, vet, `go test -race ./...`, `make test-integration`, web checks green; result lines in the PR.

#### Test plan
Dev: requirements 1 to 6 on a private stack. QA: runs everything on the PR head, re-runs two fuzz targets for 5 minutes each, tries three hostile payloads by hand against the live API (deep nesting, 10 MB body, control characters in a template name), and reads the budget numbers against a table it fills itself.
