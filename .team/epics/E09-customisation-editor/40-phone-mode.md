# E09_T-181 — Phone mode of the editor: view and light edit below 768 px

**Epic:** E09-customisation-editor · **Milestone:** M4 · **Risk:** low (web only; same document, same API, no server change) · **Priority:** P2 · **Type:** feature
**Depends on:** T-170 (page flow), T-175 (Templates panel), T-165 (History panel) merged. **Read first:** ADR 0004 (`docs/adr/0004-layout-editor.md`, Q2 phone note: handles are 9 screen px at 375 px, and decision 7 "phone mode stays view and light edit: selection, a property panel with move up/down and size buttons, text edited in the panel; no drag handles on phones"), PRD "Stage 2 plan" (owner D-42: phone = view and light edit, drag/resize/rotate from 768 px up), `web/src/pages/Editor.tsx` (below 768 px it shows the `editor.narrow` banner and mounts nothing), `web/src/book/editor/EditorShell.tsx`, `PropertyPanel.tsx`, `PageTextField.tsx` (coarse-pointer handling), `HistoryPanel.tsx`, `TemplatesPanel.tsx`, `store.ts`, `Stage.tsx`, `docs/editor-flow.md`, `docs/editor-text.md`, `docs/editor-templates.md`, `web/src/styles/editor.css`.

#### Why
A student on a phone who opens "Customise" today gets a warning that the editor needs a wide screen. Most students will first open the app on a phone. The owner decided (D-42) that phones get **view and light edit**: look at every page, change what is already there, without dragging handles that are too small to hit.

#### Requirements (SHALL)
1. **Mount below 768 px** (320 to 767 px wide, portrait and landscape): the `editor.narrow` banner goes away; the route mounts a **phone shell** over the same store, autosave, version/409 handling, history and templates code as the desktop editor. No new server route, no change to the layout document format. 768 px and up is unchanged (byte-for-byte same behaviour; the desktop e2e suite stays green).
2. **View**: the page is drawn by the same page renderer, fit to the screen width, read-only (no gesture handles, no snapping, no drag, no rotate handle); vertical scrolling of the screen is never captured by the page; the page strip becomes a bottom pager (previous/next, "Page 3 of 12", a list sheet to jump); the T-170 flow (Done, Print, Back to manage page, deep link `?page=`) works as on desktop.
3. **Select**: a tap on an item selects it (outline at least 2 px, visible on any colour); a tap outside deselects; a list of the page's items ("Layers" sheet) selects without hitting small targets.
4. **Light edit** through a **bottom sheet** (a property panel for phones, at least 44 px targets, safe-area insets respected, never covered by the on-screen keyboard: use `visualViewport`): move (four arrows, small and big steps), size (wider, narrower, taller, shorter), rotate (±5 degrees and ±90), bring forward / send back, hide/show where the desktop panel has it, delete (one confirm), duplicate if the desktop has it, colour/font/size/alignment of text and shapes with the same controls and limits as `PropertyPanel` (reuse its pure helpers; same clamps, same safe margin). **Text is edited in the sheet** in a textarea (same 500 code-point cap and the same composition handling as `PageTextField`/T-161, Vietnamese Telex/VNI on Android Gboard and iOS Safari are owner manual checks, listed in `docs/editor-text.md`). Add a text box or a sticker from the palette sheet (same palette as desktop, placed at the page centre).
5. **Undo/redo** buttons in the top bar (the keyboard shortcuts do not exist on phones); autosave status always visible in the top bar; History and Templates open as full-height dialogs (T-165 and T-175 specs already call for the dialog form on phone widths: finish that here, with focus trap, Esc/back button closes, return focus).
6. **Orientation and resize**: rotating the device or opening the keyboard keeps the selection, the open sheet and unsaved text; the layout switches between desktop shell and phone shell when the width crosses 768 px without losing state (the store is shared; the shell is a view).
7. **Performance and size**: the phone shell does not load the desktop gesture modules; check the editor route's initial JS (gzip) before and after and report it; page with 100 items scrolls and selects without jank on a 4x CPU throttle.
8. **Accessibility and i18n**: the sheet is a labelled region, every button has an accessible name, live-region announcements as on desktop, all strings vi and en (`lint:i18n` green), tap targets at least 44 px, works at 200% text size.
9. **Tests**: component tests for the phone shell (select, nudge, resize, text edit with composition events, delete confirm, pager, sheets), the shell switch at 768 px keeping state, the store untouched by view-only taps; Playwright spec `tools/e2e/editor-phone.spec.mjs` with `hasTouch` and `isMobile` at 375x812 and 414x896 and a landscape case (the Playwright browsers are Chromium based; real iOS Safari and Android Gboard are manual owner checks): open the editor from the manage page, tap an item, nudge it, resize it, edit a Vietnamese text in the sheet, add a sticker, undo, move to another page with the pager, open Templates and apply one, open History and restore, Done, reload and see the changes; the desktop suite at 768 px is run unchanged.
10. **Docs**: `docs/editor-phone.md` (what phones can and cannot do and why; the sheet; the manual checks for iOS Safari and Android Gboard with a checklist the owner can run); `docs/e2e.md` if commands change.

#### Acceptance criteria
- [ ] AC1 — On a 375x812 touch viewport a student opens the editor, selects the cover title, moves and resizes it with the sheet, edits a Vietnamese text, adds a sticker, undoes, goes to the profile page, applies a template, and after a reload sees every change; the same document opened at 1024 px shows the same result.
- [ ] AC2 — Nothing can be dragged, resized or rotated by touch on a phone, and a vertical swipe over the page always scrolls the screen.
- [ ] AC3 — Crossing 768 px (resize or rotate) swaps the shell and keeps selection, open sheet and typed text; at 768 px and wider the desktop e2e suite passes unchanged.
- [ ] AC4 — The editor route's initial JS size and the 100-item scroll check are reported in the PR; no desktop gesture module is loaded on a phone.
- [ ] AC5 — Lint, prettier, tsc, vitest, `lint:i18n`, `check:api`, build, e2e (incl. `editor-phone.spec.mjs`) and print-check green; no new dependency; nothing under `.team/`.

#### Test plan
Dev: requirement 9 on a private compose stack. QA: runs everything on the PR head; Chromium device emulation at 320, 375, 414 and 767 px portrait and landscape; text at 200%; on-screen keyboard emulation (shrink the visual viewport) with the text sheet open; two tabs (a phone edit while a desktop tab is open: one conflict banner); 100-item page; deletes an asset used by the page then opens the phone editor; resizes across 768 px mid-edit.
