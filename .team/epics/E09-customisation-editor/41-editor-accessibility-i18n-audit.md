# E09_T-182 — Accessibility and i18n audit of the editor, with fixes

**Epic:** E09-customisation-editor · **Milestone:** M4 · **Risk:** low (web only) · **Priority:** P2 · **Type:** feature/audit
**Depends on:** T-175 and T-176 merged (the last two panels). T-181 (phone shell) should be merged first so that the audit covers it; if it is not, audit desktop and tablet and list the phone shell as not covered. **Read first:** PRD "Stage 2 plan" (2c: accessibility: keyboard move/resize, labels, focus, announcements; i18n), `docs/editor-flow.md`, `editor-text.md`, `editor-history.md`, `editor-palette.md`, `editor-templates.md`, `web/scripts/check-i18n.mjs`, `web/src/book/editor/` (EditorShell, PropertyPanel, HistoryPanel, TemplatesPanel, PageStrip, Stage, gestures/), `tools/e2e/` (how specs are written), ADR 0004 (keyboard alternatives for every gesture).

#### Why
The editor was built panel by panel, each with its own accessibility notes. Nobody has walked it as a whole with a keyboard, a screen-reader checklist and Vietnamese text lengths. Students and class admins include people who cannot use a mouse; the stage 2 exit criterion says the editor must be usable, not only present.

#### Requirements (SHALL)
1. **Keyboard-only journey, written as a Playwright spec** `tools/e2e/editor-keyboard.spec.mjs` (no mouse): open the editor from the manage page, move through toolbar, page strip, stage items, property panel, palette; select an item, move/resize/rotate/reorder/delete it by keys; add a text box and type Vietnamese; add a sticker; undo/redo; open Templates, preview, apply (confirm); save a page as a template; open History, preview, restore; leave with Done; every step reachable with Tab/Shift+Tab/arrows/Enter/Esc, no keyboard trap, visible focus ring on every stop (assert computed outline or box-shadow is not none), logical order (assert the order of focus stops), focus returns to the opener when a panel or dialog closes.
2. **Names and roles**: use Playwright's `locator.ariaSnapshot()` (built in, no new dependency) to snapshot the editor in its main states (idle, item selected, text editing, Templates open, History open, a confirm dialog, error toast) and review it: every control has an accessible name in vi and en, landmarks and headings make sense, the stage items have meaningful names ("Title, text, on the cover" not "div"), selected state is exposed, dialogs are `role=dialog` with a label and `aria-modal`, status/alert regions are used for save status and errors. Keep the snapshots as test fixtures only where they are stable.
3. **Announcements**: list every live-region message the editor can send (move, resize, rotate, delete, undo, save status, apply, restore, errors); check they are polite unless urgent, not repeated on every pixel of a drag or every autosave tick (rate limit), and available in both languages; add a unit test that counts announcements for a 20-step nudge sequence.
4. **Visual**: colour contrast of the editor chrome (text and controls, including disabled and focus states) at least 4.5:1 for text and 3:1 for controls, in the themes the app has; no information by colour alone (selection, errors, save status); `prefers-reduced-motion` honoured (no animation that matters); the editor usable at 200% browser zoom and at 200% text-only zoom without clipped or overlapping controls at 1280 px width; targets at least 44 px on touch widths (spot-check with a script that measures bounding boxes of every button on tablet width).
5. **i18n**: `lint:i18n` green plus a check that no user-facing string in `web/src/book/editor/` and `web/src/pages/Editor*.tsx` is hard-coded (a lint rule or a test that greps JSX text and `aria-label`/`title`/`placeholder` literals); counts use plural-safe messages (English "1 item"/"2 items"; Vietnamese has no plural form: make sure the message works for both); dates and numbers in History and Templates use the locale; Vietnamese strings (longer than English by up to 40% in some labels) do not clip or break the toolbar, panels and buttons at 768, 1024 and 1440 px (screenshots reviewed by dev and QA, none committed unless small); the language switch inside the editor keeps the document and selection.
6. **Findings**: fix every high-severity finding (keyboard trap, unnamed control, lost focus, unreadable contrast, hard-coded string) in this task. Medium and low findings that are larger than a few lines go into a numbered list in `docs/editor-accessibility.md` with a proposed fix and size; the leader turns them into tasks. Do not hide a finding.
7. **Docs**: `docs/editor-accessibility.md`: the keyboard map (every shortcut and its alternative in the panel), the announcement list, what was tested and how, the findings table (id, severity, status), and an **owner manual checklist** for what automation cannot prove (VoiceOver on macOS and iOS Safari, NVDA on Windows with Firefox or Chrome, TalkBack on Android: 10 steps each, with expected speech), `docs/e2e.md` if commands change.
8. No new dependency (if you think an axe-based check would be worth it, say so in the PR as an option: the owner approves new packages); nothing under `.team/`.

#### Acceptance criteria
- [ ] AC1 — `editor-keyboard.spec.mjs` completes the whole journey with the keyboard only and passes 3 times in a row.
- [ ] AC2 — The aria snapshots reviewed in the PR show no unnamed interactive element, correct dialog and status roles, in vi and en.
- [ ] AC3 — A 20-step nudge sequence produces a bounded, readable set of announcements (the unit test states the bound).
- [ ] AC4 — The contrast, zoom and target-size checks pass or are listed as findings; high findings are fixed; the findings table is complete.
- [ ] AC5 — Lint, prettier, tsc, vitest, `lint:i18n`, `check:api`, build, e2e and print-check green; no new dependency; nothing under `.team/`.

#### Test plan
Dev: requirements 1 to 5 on a private compose stack, then the doc. QA: runs everything on the PR head; walks the editor by keyboard by hand once (desktop and tablet width), switches vi and en mid-edit, zooms to 200%, checks the findings table against what they see, tries to find one finding dev missed (any new finding goes on the board, not an automatic QA_FAIL unless it is high).
