# Hardening notes (not findings)

Deduplicated hunter observations, grouped by the hunter that raised them. None were independently verified.

## From `hunt-auth-session`

- Session cookie smem_session has no __Host- prefix (handler.go:296-299); a less-trusted sibling subdomain could toss a Domain-scoped cookie of the same name into a logged-out browser (acts as session fixation toward the attacker's account). Deployment dependent; renaming to __Host-smem_session (Secure, Path=/, no Domain) closes it.
- Sessions slide for 30 days with no absolute lifetime and the sliding refresh re-sends the same token (service.go:288-297); there is no sign-out-everywhere endpoint other than password reset. Consider an absolute cap and token rotation on refresh.
- Account recovery can be denied by an anonymous caller who knows the address: forgot_email allows only 3 codes per hour per address regardless of caller (service.go:34, reset.go:22), and 5 wrong guesses lock the live reset code (codes.go:71,80), so repeated attacker requests can keep a victim from resetting. Consider counting limits per (address, IP) or letting the owner of the mailbox bypass.
- Verification-code guess budget for an unverified squatter account is about 15 tries per hour sustained (3 resends x 5 tries, verify_tries 20/h), roughly 1% per month, while the victim mailbox receives 3 mails per hour. A verified squatter account would be linked as a 'verified local account' by the Google flow without stripping its password or sessions (store.go:256), so adding a cumulative cap or daily lock after N failures would harden the pre-hijack defence.
- Login, register, forgot and reset routes (no cookie) are protected from cross-site POST only by the application/json Content-Type rule and the absence of CORS; keep the invariant that any route outside auth.Guard (submit-note, lookup) must never read the session cookie or call RequireUser.
- SecureCookie is derived from cfg.Env != dev and Env defaults to dev (config.go:116); a production task that omits SMEM_ENV would also select the log mailer, public OTP key and non-Secure cookie. Owned by the peer SMEM_ENV precedence unit; consider failing start-up when SMEM_PUBLIC_BASE_URL is https but Env is dev.
- TrustProxy is not enforced or warned about in prod config (prod.go has no rule); a wrong value either shares one limiter bucket across all clients (false behind an ALB) or lets clients forge their address (true on a directly reachable task). docs/production-config.md:117-122 documents the requirement; a start-up warning when trust is on and the peer address is not private would help.
- ResolveClientIP returns the forwarded hop's raw text (middleware.go:242-243); returning net.ParseIP(ip).String() (and a /64 prefix for IPv6 keys) would give canonical limiter keys.
- Reset-password does not mark the email verified although the mailbox-delivered code proves ownership, and issues no session; this is a usability gap, not a security flaw.
- The API sets no HSTS or CSP (middleware.go:144-153); this must come from the edge, which is not in the repository.

## From `hunt-authz-data`

- internal/yearbook/service.go:128 passes the request's id string to PurgeYearbook instead of the DB-canonical y.ID, and internal/media/service.go:89-97,149 builds the S3 key from the typed yearbook_id. Return the stored public_id from ownedYearbook and use it for keys and purge. Also require canonical upper-case ULIDs on yearbook, media and note-collection routes, as the notes moderation routes already do with isPublicID. Regression test: upload with a lower-case yearbook_id, delete the book, assert no object under any spelling remains.
- internal/media/service.go:328 documents that an upload or submission racing a yearbook delete can leave orphan objects. A second DeletePrefix after Store.remove commits would close it: once the book is gone, any in-flight insert fails and its own cleanup runs, so objects written before the commit are the only leftovers.
- internal/media/store.go:155-160 (Media.keys) omits the print object when print_key is empty, but the key is deterministic (printKey(ObjectKey)). Always including it closes the interleaving in internal/media/backfill.go:85-95 where setPrintKey succeeds after Delete read an empty PrintKey, leaving a 1800 px copy of a deleted photo until the yearbook purge.
- internal/media/service.go:286 (DeleteObjects) and :307 (DeleteRows) accept raw media row ids with no owner or yearbook parameter. They are safe today only because notes.Service passes ids from owner-scoped queries; consider taking the owner-checked yearbook id and filtering by it so a future caller cannot delete another tenant's photo.
- internal/notes/service.go:225,267 and internal/notes/store.go:219 compare the deadline against the submission start time, but photo processing can take up to roughly a minute, so a submission started just before the deadline can commit after it. Use the commit-time clock if the cutoff must be exact.
- POST /api/note-collection/create has no per-user limiter, and only non-revoked rows count toward maxActive (internal/notes/store.go:55), so a verified owner can create and revoke links without bound and grow note_collection_tab. This only affects the owner's own data growth.
- internal/storage/s3.go deletes with plain DeleteObjects and no version id. If the production bucket is versioned, this only adds delete markers and old versions stay until a lifecycle rule expires them. Nothing in the repo shows the bucket configuration, so confirm noncurrent-version expiry matches the deletion promise.
- The notes next_id scope (note/get-list:<book>:<status>) does not include the owner id although docs/moderation.md describes it as user-bound. It is equivalent today because a book has exactly one owner and the query is also owner-scoped; keep it that way if sharing or transfer is ever added.

## From `hunt-config-supply`

- SMEM_ENV is not required: internal/config/config.go:116 turns an unset or empty value into dev and the Dockerfile sets no ENV SMEM_ENV. A task definition that omits it boots with the dev posture (public constant OTP and cursor key when SMEM_OTP_KEY is unset, log mailer printing codes, non-Secure session cookie, no DB/Redis/S3 TLS requirement, unrestricted metrics bind), and cmd/smemories-migrate/main.go:43 would accept 'down --allow-down' against the production database. docs/production-config.md marks SMEM_ENV 'required, must be prod' but the loader does not enforce it. Fix: set ENV SMEM_ENV=prod in the Dockerfile (compose, e2e and the smoke test already set dev or test explicitly) or refuse an unset SMEM_ENV in the API, migrate and backfill binaries. Regression test: Load with SMEM_ENV unset returns an error.
- internal/config/prod.go:45-53 checks only mc.TLSConfig == 'true' for the production DSN. A DSN with tls=true&allowFallbackToPlaintext=true (or the same parameter together with SMEM_DB_TLS_CA_FILE, which skips the DSN parse) would, from my recollection of the go-sql-driver handshake and unverified offline because no module cache exists, let a network attacker who strips the server's TLS capability force plaintext. The DSN is operator-controlled, so this is hardening: reject mc.AllowFallbackToPlaintext in prod.
- internal/config/config.go:402 accepts rediss://:@host as having credentials, because url.Userinfo.Password() reports ok for an empty password after a colon. Require a non-empty password when enforcing the prod credential rule.
- Mutable test-infrastructure inputs: bitnamilegacy/minio:2025.4.22-debian-12-r2 is tag-only in .github/workflows/ci.yml:118 and :197 and docker-compose.yml:72,90, while scripts/image-smoke.sh:27 pins it with a digest; docker-compose.yml:7 uses mysql:8.4 without a digest while CI pins one. Also unpinned: apt-get poppler-utils (ci.yml:218), the Playwright browser download (ci.yml:229) and web/.nvmrc '22'. They run only in secret-free test jobs with fake credentials and feed no release artifact. Pin the MinIO digest everywhere so one Dependabot docker PR updates all four places.
- .github/dependabot.yml covers /web but not the exact-pinned npm projects tools/e2e and tools/print-check, so playwright 1.64.0 will not receive update PRs. Add npm entries for both directories.
- .gitignore has no patterns for infrastructure state or other credential files (*.tfstate, *.tfvars, .terraform/, *.p12, credentials.json, .aws/). Add them before the IaC task T-023 lands, because this repository is public.
- The SHA-to-tag comments on the 20 pinned actions (for example checkout v7.0.1, setup-go v7.0.0, cache v6.1.0, upload-artifact v7.0.2, golangci-lint-action v9.3.0) cannot be verified offline. Owner check: confirm each SHA is the commit of the named tag in the upstream repository.
- Repository-host facts that source cannot establish and the owner should observe: branch protection and required checks on develop/main (docs/ci.md recommends four; the image and e2e jobs are not required), the repository setting for approval of fork-PR workflow runs, and the default-branch cache scoping. No workflow here uses secrets, so none of these is currently a privilege boundary.
- tools/e2e/guard.mjs:25-28 validates only the database name of SMEM_DB_DSN, not its host. A shell that exports a DSN for a remote server with a database named smem_test* would be migrated and written to by 'make e2e'. Also require a loopback host in the DSN unless E2E_ALLOW_REMOTE=1.
- tools/print-check/lib.mjs:16 runs 'npx vite' without --no-install; use 'npx --no-install vite' so a missing install fails instead of fetching an unpinned package.
- .claude/settings.json (process configuration, not a coverage unit) pre-approves Bash(make *), Bash(go run*), Bash(npm ci*), Bash(npm run *), Bash(docker compose *) and Bash(git push*) for any agent session in this checkout. Running those commands on a branch or fork pull request from an untrusted contributor would execute contributor-controlled Makefile, package scripts or Go code without a prompt. Review untrusted pull requests in a disposable environment or remove those entries.
- CI's govulncheck is blocking (ci.yml:318) while npm audit is non-blocking (ci.yml:325-328). Dependency advisory state is not assessable offline; no dependency version was judged vulnerable.

## From `hunt-injection-client`

- The SPA is not served by the Go API and web/index.html carries no CSP or framing control; the API-only SecurityHeaders (internal/httpx/middleware.go:143-153) sets X-Frame-Options DENY on API responses only. React escaping is the single XSS control, so a deployed CSP (default-src 'self'; img-src 'self' blob:; frame-ancestors 'none'; base-uri 'none') and X-Frame-Options on the SPA host are cheap defence in depth. Not a finding today: the session cookie is HttpOnly SameSite=Lax and is withheld from cross-site frames.
- Registration lets anyone have a verification email sent to an arbitrary address with an attacker-chosen display name (up to 100 characters, URL-like text allowed) in the greeting (internal/auth/mail.go:81, emails/en.tmpl:2,7). The HTML part is escaped by html/template, so this is content spoofing from the app's trusted sender, not XSS. Consider dropping the name from unverified-address emails or restricting its charset.
- web/src/auth/errors.ts:46-47 safePath blocks only a leading // or /\ and does not reject control or format characters, unlike the server's safeReturnTo (internal/auth/google.go:300-310). It is safe today because it only sees router-generated pathname+search and the server re-validates; align it before any new caller feeds it external strings.
- web/src/i18n.ts:43 sets escapeValue:false. It is safe as long as no Trans component, dangerouslySetInnerHTML or HTML-returning t() is added; an eslint react/no-danger rule would lock that in. Verify i18next 26 keeps skipOnVariables true so a $t(key) typed into a note name is not resolved by nesting (worst case would be showing another locale string, not markup).
- web/src/auth/errors.ts:43 uses `e.code in FIELD_OF` on a plain object, so a server code such as ERROR_CONSTRUCTOR would hide an error banner; use Object.hasOwn. The code is server-controlled, so no attacker path.
- internal/media/handler.go:197-206 stores any 64 bytes (control characters, invalid UTF-8, ignorable characters that still collate equal) as the yearbook_id used in S3 keys. Keys with XML-invalid control characters could make DeleteObjects or listing fail for that owner's own photos or yearbook (self-inflicted lockout, not observed); canonical-id validation fixes it with the candidate above.
- internal/media/handler.go:136 binds the page-token scope to the caller's spelling of yearbook_id and toJSON echoes it (line 117); both are harmless today and become canonical once ids are validated.

## From `hunt-logic-wildcard`

- Media quota counts only len(p.display) (internal/media/service.go:150) while the print and thumb objects are stored too (service.go:152-162); for photos of 1800 px or less the print object duplicates the display bytes, so real S3 use per user can reach roughly 2x the 500 MiB constant (store.go:15) plus thumbnails. Count all stored bytes or document the factor.
- save() pre-checks the quota with add=0 (internal/media/service.go:121), so when the owner is within one photo of the 500 MiB limit every upload is fully decoded, re-encoded, written as 3 objects and deleted again before ErrQuota at store.go:103; pass an upper bound for the new size to the pre-check.
- The processing-slot release is a plain statement, not a defer (internal/media/service.go:137-143): a panic inside load() or process() is caught by the Recover middleware but leaks a slot permanently (default 2 slots), after which owner uploads wait forever and contributor uploads return ERROR_BUSY until restart. Use defer or recover around the slot section.
- Contributor photos share the owner's 200-photo / 500 MiB quota with no per-link or reserved owner budget (internal/media/service.go:115, store.go:75): one holder of a widely shared link can fill a yearbook's 200 photos in about 67 submissions (60 per hour per link) and block the owner's own uploads and other friends' photos with ERROR_QUOTA_EXCEEDED until the owner deletes notes or revokes the link. Consider a per-link photo cap or a reserved owner allowance.
- notes.SubmitNote refunds all four counters on ErrBusy even when earlier photos of the same request were already decoded, stored and then discarded (internal/notes/service.go:242-248); refund only when no photo was processed, otherwise a request can cost S3 and DB work without being counted.
- Rate-limit keys for IP budgets are the raw address string from httpx.ResolveClientIP (internal/httpx/middleware.go:247-251, used at notes/service.go:162 and by the auth limiters): an attacker with an IPv6 prefix gets a fresh budget per address. Group IPv6 by /64 before keying. The largest effect is on register/login limiters owned by peer units; within the notes routes the per-collection limit and the 300-note cap still hold.
- The public submission path has no CAPTCHA (notes/verifier.go:15-17 allowAll, handler.go:43) and a filled honeypot field returns success after the body was spooled without taking any submit limiter (notes/submit.go:124-127), so only public_all (600 per 15 min per IP) and the connection slots bound that path.
- smemories-migrate refuses down only when SMEM_ENV=prod (cmd/smemories-migrate/main.go:43), SMEM_ENV defaults to dev (internal/config/config.go:116) and the Dockerfile sets no ENV, so a one-off task run against the production DSN without SMEM_ENV=prod can execute destructive down migrations. Tie the refusal to the target (for example a marker row in app_meta) or require an explicit ALLOW flag in addition.
- Dev-selected behaviours are neither tagged DEV-SHORTCUT nor registered in docs/dev-shortcuts.md: the public devOTPKey fallback for SMEM_OTP_KEY (config.go:83,359-361; it also keys the cursor tokens), the log mailer, Secure=false cookies when SMEM_ENV=dev (main.go:135) and localhost defaults for origins and base URL. They are safe only because prod refuses them, and the planned scripts/check-no-dev-shortcuts.sh (does not exist yet) will not see them; the four *_ALLOW_INSECURE opt-outs (prod.go:20-34) are likewise unregistered transport weakeners.
- .gitignore does not cover .env.development, .env.test, .env.*.local, *.p12, *.pfx, *.tfvars, terraform state or credentials.json; only .env.example is tracked today.
- .claude/settings.json pre-approves Bash(make *), go run, npm install and git push for any Claude Code session opened in the repo, so build files from an untrusted branch execute without a prompt; developer-environment risk only.
- design/canvas/temp1-8.html (about 15 MB of compressed design bundles with scripts) is tracked but is not part of the image or the web build; remove it from the public repo or document its origin.
- API responses carry no Strict-Transport-Security or Content-Security-Policy header (internal/httpx/middleware.go:144-153); this is fine only if the edge adds them, which is outside the repository.
- ratelimit.Redis.Refund pops the newest hit of the key, not the caller's own (internal/ratelimit/redis.go:51); counts stay correct, but a lost or duplicated Refund after a Redis error shifts the budget by one, so keep fail-closed limiters free of refund paths that run after a failed Take.

## From `hunt-oidc-crypto`

- codes.go:125-129 keys the email-code HMAC with the raw SMEM_OTP_KEY while cursor.go:25-28 derives its key with a label, and nothing rejects SMEM_OIDC_COOKIE_KEY equal to SMEM_OTP_KEY (config.go loadGoogle/loadOTP). I found no cross-protocol collision today, but deriving every key with a distinct label from one master, or rejecting equal values, would remove the foot-gun.
- In dev and test the OTP key is the public constant devOTPKey (config.go:83) and the cursor key derives from it, so cursor tokens are forgeable there. This is harmless for authorization because positions are only integers or ids inside the caller's own list. The environment-default precedence is owned by a peer unit.
- The smem_oidc and smem_session cookies have no __Host- prefix and Path=/ (google.go:168-173, handler.go:295-299). If a sibling subdomain can set cookies in the deployed layout, an attacker could plant a valid flow cookie and cause login CSRF. Using __Host- names would close this, and it needs no attacker-visible change.
- SignInGoogle links any new Google subject to a local user found by email even if that user already has a different Google subject (store.go:243-266). The unique key is only (provider,subject), so there can be several per user. This gives no more power than email-based password reset, but refusing a second subject for an existing Google-linked user would block the recycled-email case.
- Pin the ID-token algorithm explicitly with oidc.Config{SupportedSigningAlgs: []string{oidc.RS256}} instead of relying on the go-oidc v3.21.0 default (google.go:259).
- Sessions slide for 30 days with no absolute lifetime (service.go:288-297), so a stolen cookie that is used at least every 15 days never expires. An absolute cap, for example 90 days, would limit it.
- SMEM_AUTH_ARGON_MEMORY_KIB, TIME and PARALLELISM accept values down to 8 KiB, 1 and 1 even when SMEM_ENV=prod (config.go:201-212). Add a prod floor at the default 19456/2/1.
- internal/auth/oidctest is a fake IdP in a non-_test package. No non-test file imports it today (grep), but keep it out of cmd imports or move it under a _test or build-tagged file so it can never be linked into the production binary.

## From `hunt-public-obs`

- The link token travels in the query string (GET /api/public-collect/get, POST submit-note) and also in the SPA path /c/:token. App logs omit it, but any ALB or CloudFront access log that records URLs would capture it whatever the API transport. When T-023 lands, disable or restrict URL logging for /c/* and /api/public-collect/*, or move the token to the URL fragment plus a header or body field.
- Add X-Robots-Tag: noindex at the edge for /c/*; the noindex meta is injected by JavaScript only after load (NoteForm.tsx).
- GET /readyz and /healthz are unauthenticated and /readyz takes a pooled DB connection and does a Redis SET per request with no limiter. Keep /readyz off the public listener or cache its result for about a second.
- SMEM_METRICS_ALLOW_ANY_INTERFACE=true binds the unauthenticated metrics listener to every interface. The only control is a security group that is not in the repository, so verify the metrics port is absent from the ALB target group and from public security-group rules.
- LogMailer prints codes to the same stdout stream as the JSON app log; this is safe only because NewLog and loadMail refuse non-dev/test and non-ses prod. SMEM_ENV=test is accepted by config and also gets the public dev OTP key; make sure no deployed environment uses dev or test.
- Print-feedback counters can be skewed at 30 per IP per hour and have no consumer in code. If the numbers ever drive a decision, treat them as untrusted telemetry.
- Google sign-in falls back to the email local part as display_name (google.go:333-339), which the public link lookup returns to link holders. Prefer a neutral default such as 'Student'.
- NoteForm persists text drafts in localStorage keyed by a token hash on the device until the note is sent. On a shared computer a later visitor opening the same link sees the earlier draft; consider sessionStorage.

## From `hunt-upload-resource`

- internal/media/image.go:74-78: the print variant is scaled and encoded in a goroutine (wg.Go) with no recover; a panic there would terminate the whole process, not one request (the Recover middleware only covers the handler goroutine). No panic input was found; wrap the goroutine body in a recover that returns an error.
- internal/media/service.go:137-142: release the processing slot with defer so a decoder panic cannot leak it (also see candidate media/process-header-dims-trust-and-sem-release-without-defer).
- internal/media/image.go:200-222: decodedBytes undercounts two cases verified in the Go 1.26 stdlib: 4-component (CMYK/YCCK) JPEG allocates an extra 4 bytes per pixel in applyBlack (image/jpeg/reader.go:675-738) on top of the 2.5-4 counted, and Adam7-interlaced PNG allocates per-pass images on top of the full image (image/png/reader.go:375-390, up to about 1.5x). The worst cases stay near the already-measured 490 MB per slot in docs/media.md, but the 128 MiB estimate is not the true peak; add a factor for 4-component JPEG and interlaced PNG or re-measure.
- internal/media/service.go:73,94: the 60-uploads-per-10-minutes limiter is per user id and gives no fairness on the 2 shared processing slots; a handful of free accounts (registration is limited per raw IP only) uploading 50 MP JPEGs of a few hundred KB can keep both slots busy and make owners wait and contributors get 503 after 10 s. A per-owner or per-IP concurrency cap on slots would bound it (limiter unit is owned by a peer).
- internal/media/store.go:75 and service.go:150: quota counts only len(display) bytes, so thumbnail and print objects (roughly +30-50%) are uncounted storage (quota unit is owned by a peer).
- internal/media/handler.go:268-287: HEAD, If-None-Match and Range requests on get-content still fetch the whole object from S3 before ETag/Range are evaluated; consider evaluating the ETag from the database row first.
- internal/notes/submit.go:136-137 and verifier.go:17: the CAPTCHA hook runs after the 32 MiB body is spooled and the default verifier is allowAll, so even when wired it cannot gate disk or connection cost; run it before spooling or after Resolve for first-time IPs.
- internal/notes/spool.go:18-26: CheckSpool could also check free space against SMEM_PUBLIC_UPLOAD_MAX_CONNS x maxBody and refuse to start (or lower the cap) when the spool is smaller.
