# Needs validation: unresolved leads (no severity)

Each lead is a source-grounded hypothesis blocked on a specific fact. They are not confirmed vulnerabilities. Plans are bounded and non-destructive: run local steps only in an OS-enforced sandbox with dummy data, and deployment steps are owner-observed reads. Never send audit traffic to a live system.

## 1. Login lockouts are keyed only on the exact client-IP string, so guesses against one account scale with the attacker's address pool (IPv6 rotation)

- Fingerprint: `auth/login-throttle-keyed-on-raw-ip-no-account-counter`
- Affected boundary: Anonymous -> per-account password-guess budget
- Candidate raised by: `hunt-auth-session`; independently verified by a fresh verifier who kept it as `needs_validation`.

### Claim
Service.Login takes two fail-closed sliding-window limiters, login_pair (key = ip + '|' + sha256(email), 10 per 15 min) and login_ip (key = ip, 100 per 15 min). Both keys contain the client address as an exact string. ResolveClientIP returns the RemoteAddr host, or the trimmed text of the last X-Forwarded-For hop when SMEM_TRUST_PROXY is on and the hop parses as an IP. It does not group IPv6 addresses by prefix and does not canonicalise them. No limiter on the login path is keyed on the account alone. This is the only password-guessing path with that shape: forgot_email, verify_tries and username_tries are already keyed on the account. An attacker who can present many distinct source addresses (an IPv6 /64 if the production ingress accepts IPv6, or an IPv4 proxy pool at higher cost) starts a fresh 10-guess budget per address against the same victim email every 15 minutes, so the 'fail closed to stop guessing' control does not bound online guessing per account. The password policy is only 10 to 128 characters (NFKC-normalised, not equal to the email) with no breached-password or denylist check, so common passwords of 10 or more characters stay within reach. Throughput is bounded by the hashing slots (default 4 concurrent Argon2id computations with m=19456 KiB, t=2, p=1, and a 2 s slot wait). Address-rotating traffic could also contend with legitimate logins for those slots. That throughput and contention have not been measured. The key-space property is statically visible. Whether it is reachable in production depends on ingress addressing, trusted-proxy configuration, edge controls, and the owner's intent, none of which are in the repository.

### Claimed root cause
The lockout key space is the attacker-expandable set of exact client-address strings; there is no per-account (email-only) failure counter and no IPv6 prefix grouping, so the per-account guess rate is unbounded for an attacker with address diversity.

### Source trace
1. `internal/auth/handler.go:129` (entrypoint, Handler.login (POST /api/auth/login, registered at handler.go:45)): Anonymous JSON request {email, password}; no session is needed. The handler passes h.clientIP(r) (line 134; defined at lines 306-308 as httpx.ResolveClientIP with the SMEM_TRUST_PROXY flag) as the ip argument of Service.Login.
2. `internal/httpx/middleware.go:238` (propagation, ResolveClientIP): Returns the RemoteAddr host (net.SplitHostPort, lines 247-251), or with trustProxy the last X-Forwarded-For hop when net.ParseIP accepts it (lines 239-244). The hop is returned as its trimmed original text, so IPv6 addresses are neither grouped to a prefix nor canonicalised.
3. `internal/auth/service.go:196` (propagation, Service.Login): pairKey = ip + '|' + hashKey(email). Take on login_pair (line 200) then on login_ip (line 207); no Take keyed on the email alone exists on this path. A passed Take lets the request reach userByEmail and the Argon2id Verify (lines 221-235).
4. `internal/ratelimit/redis.go:181` (sink, Redis.key / Redis.Take): key() builds smem:<env>:rl:<name>:<that exact string> (redis.Client.Key joins the parts, internal/redis/redis.go:101), and Take runs the sliding-window script on it (line 194). A previously unseen address string is an empty sorted set with a full budget, so lockout state is not shared across address strings.

### Verified evidence
- `internal/auth/service.go:196`: Lockout key construction uses the raw ip string; the only other limiter on Login (login_ip, line 207) is also keyed by ip. Both limiters are created at lines 98-99.
- `internal/httpx/middleware.go:247`: Without a trusted proxy the key is the net.SplitHostPort(RemoteAddr) host verbatim (returned at line 251), so every IPv6 address is its own key.
- `internal/auth/validate.go:60`: validPassword accepts any password of 10 to 128 characters that differs from the email; it is the only check (callers: service.go:144, reset.go:56), and a grep of internal/ finds no breached-password or denylist logic.
- `internal/config/config.go:216`: SMEM_RATE_LOGIN_FAILS_PER_EMAIL defaults to 10 (per IP+email); line 219 sets SMEM_RATE_LOGIN_FAILS_PER_IP to 100. No account-level setting exists.
- `internal/config/config.go:197`: SMEM_AUTH_MAX_CONCURRENT_HASHES defaults to 4 (Argon2id defaults at lines 201-212; HashWait is 2 s at auth/service.go:25, slot wait in password.go:49-60). This bounds, but does not remove, per-account guess throughput.
- `docs/redis.md:101`: The documented limiter table lists login_pair keyed on 'IP + hashed email' and login_ip keyed on 'IP' (line 102), with no account-only counter and no stated rationale for omitting one.
- `internal/auth/integration_test.go:720`: The existing integration test (read, not run) asserts that after the pair limit is hit, a login from another RemoteAddr succeeds ('another IP is not affected'), and lines 785-795 assert that distinct trusted forwarded hops are distinct clients. This encodes per-address-string keying as intended behaviour.
- `internal/auth/service.go:106`: Calibration only: forgot_email is keyed on hashKey(email) alone (reset.go:22), and verify_tries and username_tries are keyed per user id, so account-keyed limiters exist in the same package; the login path has none.

### Exact blockers
- Ingress addressing is not in the repository (no IaC): whether production serves IPv6 clients (load balancer IP address type dualstack or ipv4, public AAAA record) decides how cheaply an attacker obtains many distinct limiter keys. IPv4 proxy pools also bypass a per-address key, at higher cost.
- The effective SMEM_TRUST_PROXY value, the real proxy chain (whether the last X-Forwarded-For hop is the true client address) and any edge or WAF rate rule on POST /api/auth/login are deployment facts. If trust is off behind a load balancer, all clients share one key, which is a different failure mode.
- The owner's intent is not in source: docs/redis.md:101-102 documents the keys without rationale. Whether omitting an account-only counter is an accepted trade-off against attackers locking victims out decides whether this is a defect or a recorded decision.

### Bounded local resolution plan
ratelimit.NewMemoryFactory alone cannot drive Login, because Login reads the user through the MySQL-backed Store. Use the owner's local, non-production dev stack (own compose project name and ports; dummy data only). Make a scratch copy of the integration harness (internal/auth/integration_test.go, build tag integration, newEnv). It may swap ratelimit.NewFactory for ratelimit.NewMemoryFactory(clock.now) to avoid Redis; MySQL via dbtest.New is still needed. Pass Limits explicitly, because a zero Limits is replaced by 1000/1000/1000 at integration_test.go:83-85: Limits{RegisterPerHour: 100, LoginFailsPerPair: 10, LoginFailsPerIP: 100}. Register one dummy account (alice@example.com and the obviously fake test password). (a) Control: 11 wrong-password logins from RemoteAddr '[2001:db8::1]:4000'; expect the first 10 to answer 401 ERROR_INVALID_CREDENTIALS and the 11th 429 ERROR_RATE_LIMITED. (b) Test: 200 wrong-password logins for the same email, the i-th from RemoteAddr '[2001:db8::<i+1>]:4000'; the current code is expected to answer 401 for all 200 and never 429, so 200 judged guesses against a nominal budget of 10. (c) Repeat with the harness option trustProxy: true and 'X-Forwarded-For: 2001:db8::<i+1>' headers to confirm each distinct forwarded hop is its own key. (d) Optional severity input: time Hasher.Verify with the production defaults (m=19456, t=2, p=1, 4 slots, 2 s wait) under concurrent load to estimate sustained guesses per second and whether ErrBusy (503) appears for a concurrent legitimate login. Nothing here touches a deployment.

### Owner-observed deployment check
Read-only owner observation, no traffic sent: (1) the load balancer's IP address type (dualstack or ipv4) and whether a public AAAA record exists for the API/app hostname; (2) the SMEM_TRUST_PROXY value in the running task/container configuration and whether the proxy chain appends the real client address as the last X-Forwarded-For hop; (3) whether any ALB/WAF/CDN rate-based rule covers POST /api/auth/login; (4) the owner's recorded decision on an account-level failure counter, set against lockout abuse, if IPv6 is not served and no per-account throttle is wanted.

## 2. A login that verified the old password can create a session after the password-reset or Google-merge session purge

- Fingerprint: `auth/session-create-not-fenced-against-credential-purge`
- Affected boundary: Password reset / Google pre-hijack session revocation vs in-flight login
- Candidate raised by: `hunt-auth-session`; independently verified by a fresh verifier who kept it as `needs_validation`.

### Claim
Service.Login reads the user and password hash with a plain autocommit SELECT (service.go:221, store.go:144), may then wait up to HashWait (2 s, service.go:25; 4 hashing slots by default, config.go:197) for an Argon2id slot, verifies against the hash it read earlier, refunds both login limiters (service.go:234) and calls issue, which stores a session through Sessions.Create (service.go:251). Create's Lua script (sessions.go:40-50) writes the session hash and adds it to the user's index unconditionally. The only two credential purges, ResetPassword (reset.go:74, store.resetPassword) and the Google pre-hijacking defence for an unverified local account (google.go:344, store.go:248-269), call Sessions.DeleteAll inside the DB transaction before Commit (reset.go:85-91; store.go:248, 252, 269). deleteAllScript removes only the sessions that are members of the user's index at that moment (sessions.go:72-75). A login whose row read happened before the purge and whose Create runs after it therefore leaves a live session, and Authenticate (service.go:263-299) checks only session existence/expiry and loads the user by id; no per-user credential epoch exists anywhere, and DeleteAll has no other caller. The flaw needs no database-isolation assumption for a login whose read precedes the UPDATE; a read between the UPDATE and Commit additionally relies on InnoDB's non-locking read returning the last committed (old) row, which db.Normalize leaves at the server default (db.go:33-45). The attacker must already know the credential that is being revoked: the old password after a reset, or the squatter's own password in the pre-hijack case, where the surviving session ends up on an account that is now email-verified and linked to the real owner's Google identity. Both limiters are refunded on a correct password (defaults 10 per IP+email and 100 per IP per 15 min, config.go:216-219), so a loop of correct-password logins is not throttled, and the post-read slot wait lengthens the exposed window. The interleaving is deterministic once scheduled but has not been observed in this audit; existing tests exercise only sequential flows (google_integration_test.go:259-285) and Extend-versus-Delete races (sessions_integration_test.go:194-228).

### Claimed root cause
Session creation in Login is not fenced against the credential purge: the user row is read without a lock or credential version, Argon2id verification runs outside any transaction, and Sessions.Create stores the session unconditionally, while the purge (DeleteAll) runs before the credential change commits and removes only sessions that already exist. Nothing binds a session to the credential state it was issued under, so a login that read the old credential can create a session that survives the purge and then slides for 30 days with no absolute cap.

### Source trace
1. `internal/auth/handler.go:129` (entrypoint, Handler.login (POST /api/auth/login)): Anonymous caller repeatedly submits the known password of the target account (the old password after a reset, or the squatter's own password for a pre-registered unverified account); the handler passes it to Service.Login (line 134).
2. `internal/auth/service.go:221` (propagation, Service.Login): userByEmail returns the user and the current password hash from a plain autocommit SELECT (store.go:144, s.db.QueryRowContext), with no transaction, lock or credential version. It does not wait for a concurrent UPDATE of the same row.
3. `internal/auth/password.go:104` (propagation, Hasher.Verify): After the row was read, Verify waits up to HashWait (2 s) for one of the hashing slots (4 by default), then runs Argon2id against the old hash it already holds. This sits between the credential read and the session write.
4. `internal/auth/reset.go:85` (propagation, Store.resetPassword): Counterpart actor: UPDATE password_hash (85), dropSessions = Sessions.DeleteAll (88), Commit (91). The purge precedes the commit by design, so concurrent plain reads still see the old hash until line 91.
5. `internal/auth/store.go:248` (propagation, Store.googleUserTx (pre-hijacking defence)): Counterpart actor for the Google merge: SELECT ... FOR UPDATE (243, blocks only locking readers), UPDATE password_hash=NULL and mark verified (248), DeleteAll (252), identity INSERT, Commit (269). Login's non-locking read is not blocked by the FOR UPDATE.
6. `internal/auth/service.go:234` (propagation, Service.Login / Service.issue): On a hash match Login refunds both limiters (234) and calls issue (235), which mints a token and calls Sessions.Create (251) without re-reading the credential or passing any epoch.
7. `internal/auth/sessions.go:40` (sink, createScript / Sessions.Create): The create script HSETs the session hash (40) and SADDs it to the user's index (49) unconditionally, after DeleteAll has already emptied the index. Authenticate (service.go:269-281) then accepts it because it checks only existence, last_seen_at and that the user row exists.

### Verified evidence
- `internal/auth/service.go:221`: Login reads the user and hash before waiting for a hashing slot; no transaction or lock.
- `internal/auth/store.go:144`: userByEmail is a plain s.db.QueryRowContext SELECT, not a locking read.
- `internal/auth/password.go:104`: Verify acquires a hashing slot only after the row was read; the wait is bounded by Hasher.wait (HashWait = 2 s, service.go:25, wired at cmd/smemories-api/main.go:111).
- `internal/auth/service.go:234`: Both login limiters are refunded on a password match before issue, so correct-password logins do not accumulate against the defaults of 10 per IP+email and 100 per IP (config.go:216-219).
- `internal/auth/service.go:251`: issue calls Sessions.Create with no credential-version or epoch argument.
- `internal/auth/reset.go:88`: dropSessions (DeleteAll) runs before tx.Commit at line 91, so the old hash is still the committed value while the purge has already happened.
- `internal/auth/store.go:252`: Google merge has the same order: UPDATE (248), dropSessions (252), Commit (269); the FOR UPDATE at 243 does not affect Login's non-locking read.
- `internal/auth/sessions.go:72`: deleteAllScript deletes only the members of the user's index present when it runs; a session created afterwards is untouched.
- `internal/auth/sessions.go:49`: createScript ends with an unconditional SADD into the user index and has no epoch, generation or existence check.
- `internal/auth/service.go:269`: Authenticate does Lookup (269) then userByID (281) and only slides expiry (288-297); there is no check that the session is newer than the last credential change, and the User row carries no credential version (store.go:57-66).
- `internal/auth/google.go:344`: SignInGoogle passes s.sessions.DeleteAll into googleUser; together with reset.go:74 these are the only DeleteAll callers in the repository.

### Exact blockers
- No target code may be executed in this audit and no MySQL 8.4 / Redis harness is available to this reviewer, so the decisive interleaving (credential row read before the purge, Sessions.Create after DeleteAll, then GET /api/user/get-me accepting the new cookie) has not been observed. The source establishes the missing fence and the order of the two atomic Redis scripts, but not that the surviving session is accepted end to end.

### Bounded local resolution plan
Use the existing package-auth integration harness (newEnv in internal/auth/integration_test.go, throw-away MySQL via dbtest and Redis via redistest, nothing deployed). Create the env with opts{maxHashes: 1, hashWait: 30 * time.Second} and register an unverified account (email E, password P) through the real register path. Variant A (Google merge, read before the UPDATE): (1) hold the only hashing slot with e.hasher.slots <- struct{}{}; (2) start e.svc.Login(ctx, "192.0.2.1", "ua", E, P, "") in a goroutine; it reads the row, then blocks in Hasher.acquire; wait about 300 ms; (3) run e.svc.SignInGoogle(ctx, "ua", "", &GoogleIdentity{Subject: "s1", Email: E, Name: "V"}) to completion (it needs no hash slot) and assert the row now has password_hash IS NULL and email_verified_at IS NOT NULL; (4) release the slot with <-e.hasher.slots and collect the goroutine's *Session; (5) call e.svc.Authenticate(ctx, sess.Token). A nil error confirms a session surviving the purge on the now-verified account; ErrUnauthenticated (or Login returning ErrInvalidCredentials) refutes the candidate. Variant B (reset): compute phc = e.hasher.Hash(ctx, newPW) before holding the slot, repeat steps 1-2, then call e.svc.store.resetPassword(ctx, uid, phc, now, e.sess.DeleteAll) (the same function ResetPassword calls at reset.go:74) in place of step 3, then steps 4-5. Variant C (read while the transaction is open, which also observes the MySQL visibility fact): call e.svc.store.resetPassword with a dropSessions wrapper that calls e.sess.DeleteAll and then, before returning, runs e.svc.Login(E, oldPW) synchronously with the slot free and records its result; after resetPassword returns, Authenticate the token. A successful Login during the open transaction shows the non-locking read returns the old hash; a surviving token confirms the flaw. Control: run Login only after resetPassword or SignInGoogle has returned; it must give ErrInvalidCredentials, which shows the fixture is sensitive. Repeat each variant about 20 times to rule out flakiness. Suggested fix to test with the same fixture: a per-user purge epoch (for example a Redis key bumped inside deleteAllScript) read before the credential lookup and passed to createScript, which refuses to store the session when the epoch changed, together with a purge that also runs after the credential commit; all variants should then end in ErrUnauthenticated.

## 3. Owner photo upload and yearbook delete build S3 prefixes from the caller's spelling of the yearbook id instead of the canonical database id

- Fingerprint: `media-s3-prefix-from-caller-yearbook-id-spelling`
- Affected boundary: Owner delete -> object-store deletion guarantee
- Candidate raised by: `hunt-injection-client`; independently verified by a fresh verifier who kept it as `needs_validation`.

### Claim
Source review supports the path, and only the MySQL comparison semantics (not observed in this audit) decide whether it is reachable. POST /api/media/create reads the multipart field yearbook_id with only a 64-byte length cap, and POST /api/yearbook/delete reads id with only a non-empty check. Both resolve the book with WHERE owner_id = ? AND public_id = ? on yearbook_tab.public_id, which is CHAR(26) in a utf8mb4_0900_ai_ci table, queried over a connection forced to the same collation. The repo's own notes code says these columns compare case-insensitively. If that holds, a lower-cased or accent-varied spelling of the caller's own ULID selects the caller's own row. media.Service.Upload then passes the caller's string, not the database value, to save, which writes yearbooks/<spelling>/<ulid>.<ext>, -thumb.jpg and -print object keys. The contributor (friend link) path instead reads public_id from the database and uses the canonical prefix. yearbook.Service.Delete loads the canonical row y (y.ID) but calls PurgeYearbook with the request's publicID. That becomes S3.DeletePrefix('yearbooks/<spelling>/'), a ListObjectsV2 prefix match that only finds keys with exactly that spelling. The row deletion afterwards uses the canonical row (lockBook with y.ID, deleteBook by internal id), so rows are removed whatever the objects' fate. Resulting states: (a) objects uploaded under spelling A survive a delete issued with spelling B or the canonical id; (b) canonical-prefix objects (the SPA's own uploads and friends' photos) survive a delete issued with any non-canonical spelling. Survivors have no row, are unreachable through the API, and are not counted by checkQuota, which sums media_tab rows only, so they also fall outside the owner's 500 MiB quota accounting. No sweeper exists in the repo; media/service.go:328 only says one is planned for M2. Single-photo deletes and moderation deletes use the keys stored in the rows and are unaffected. The web client always sends the id it received from the API (web/src/api/yearbooks.ts:43,90), so a non-canonical request needs a hand-built API call by the owner. Scope is the caller's own books: the UNIQUE key means no other owner's ULID can be collation-equal to the caller's, and the prefix ends with a slash, so no sibling book is reachable. Collation-equal spellings could include accent marks or default-ignorable code points, but not '/' or '.', so key structure is not escapable. The notes and bookdata packages already reject non-canonical ids (notes/moderation.go isPublicID, whose comment names this exact reason). Suggested fix: share one canonical-ULID check (26 upper-case Crockford characters) and apply it in the media and yearbook handlers (or services) for every id-taking route. Compose yearbookPrefix and PurgeYearbook from the database value (the row's public_id / y.ID), never from the request string. Add regression cases: upload with a lower-cased yearbook_id returns 400 (or lands under the canonical key), and delete with a lower-cased id returns 400 or leaves zero objects under yearbooks/<canonical>/.

### Claimed root cause
Id canonicalisation is enforced in the notes and bookdata packages but not in the media and yearbook handlers or services. Those services build the S3 key prefix (upload) and the purge prefix (yearbook delete) from the request string rather than the canonical public_id they resolve from the database, while the database lookup tolerates other spellings.

### Source trace
1. `internal/media/handler.go:196` (entrypoint, Handler.readForm): POST /api/media/create: the multipart field yearbook_id is read as is (line 197). The only check is a 64-byte length cap (maxIDBytes, line 24; lines 202-205), then it is assigned at line 206. Handler.create passes it on at lines 108 and 112.
2. `internal/media/service.go:97` (propagation, Service.Upload): The same request string goes to Store.ownedYearbook (line 90) and, unchanged, to save as yearbookID (line 97).
3. `internal/media/store.go:54` (propagation, Store.ownedYearbook): Ownership is resolved with WHERE owner_id = ? AND public_id = ?. Under the declared utf8mb4_0900_ai_ci collation this is expected to accept any collation-equal spelling of the caller's own ULID (not observed here).
4. `internal/media/service.go:149` (propagation, Service.save): ObjectKey, ThumbKey and PrintKey are built as yearbooks/<yearbookID>/... from the string passed in by Upload (lines 149-150) and stored in media_tab by insert (store.go:106-109). The contributor path passes the database public_id instead (lines 111-115).
5. `internal/yearbook/handler.go:131` (propagation, Handler.delete): Second HTTP entry of the same defect: POST /api/yearbook/delete only checks id is non-empty (required, lines 54-59) and calls Service.Delete.
6. `internal/yearbook/service.go:128` (propagation, Service.Delete): After loading the canonical row y (line 123), PurgeYearbook is called with the request's publicID rather than y.ID. The rows are then deleted via the canonical row (store.go:422-433).
7. `internal/media/service.go:330` (propagation, Service.PurgeYearbook): Builds yearbookPrefix(yearbookID) from whatever string the caller supplied and calls DeletePrefix.
8. `internal/storage/s3.go:181` (sink, S3.DeletePrefix): ListObjectsV2 with Prefix yearbooks/<request spelling>/ only matches keys with exactly that spelling. Objects written under another spelling, or under the canonical prefix, survive while the book and photo rows are deleted.

### Verified evidence
- `migrations/0004_yearbooks_profiles.sql:21`: Table collation utf8mb4_0900_ai_ci; public_id is CHAR(26) at line 6 with a UNIQUE key at line 18.
- `migrations/20261010120000_yearbook_tab_conventions.sql:8`: The table is renamed to yearbook_tab (line 8) and the unique index renamed (line 18). No migration changes the public_id column type or collation (searched all migrations).
- `internal/db/db.go:43`: Connection collation is forced to utf8mb4_0900_ai_ci, the same as the column.
- `internal/notes/moderation.go:123`: isPublicID comment: the public_id columns compare case-insensitively, so anything but a canonical upper-case ULID would match a row under another spelling. The check (lines 108-135) exists only in notes (and bookdata through it), not in media or yearbook.
- `internal/notes/moderation_qa_integration_test.go:10`: Team QA test comment states the column collation is case-insensitive and that a differently-cased id matches the row; no equivalent test exists for media or yearbook.
- `internal/media/handler.go:112`: Upload is called with the unvalidated yearbookID; the response also echoes the caller's spelling (line 117).
- `internal/media/store.go:126`: yearbookByRow reads owner_id and public_id from the database for the contributor path, so friend photos always use the canonical prefix.
- `internal/yearbook/store.go:247`: Store.get (used by Delete) matches owner_id = ? AND public_id = ? with the same tolerant comparison, then scanBook fills y.ID from the database column.
- `internal/media/store.go:71`: checkQuota counts media_tab rows only (lines 67 and 71-72), so objects left in the bucket after the rows are deleted are not counted against the owner's quota.
- `internal/media/service.go:328`: ponytail comment: a periodic sweep of keys without rows is planned for M2; no such sweep exists in the repository.
- `web/src/api/yearbooks.ts:43`: The SPA sends the id it received from the API (delete line 43, upload form field line 90), so a non-canonical spelling needs a hand-built request by the owner.

### Exact blockers
- The decisive precondition has not been observed: that MySQL 8.4 matches the CHAR(26) public_id with a differently-cased or accent-varied literal under utf8mb4_0900_ai_ci on this connection. Source gives the DDL, db.go:43 and the team's own comments and test, but no run was permitted. If the match were exact, ownedYearbook and Store.get would return NOT_FOUND for any non-canonical spelling and the candidate would be rejected.
- Whether leftover objects persist or matter depends on bucket lifecycle, versioning, replication and access policy and on any sweeper the operator runs. None of these exist in the repository (no IaC, bucket policy or sweeper), and this audit cannot observe a deployment.

### Bounded local resolution plan
Use a throwaway MySQL 8.4 plus MinIO stack with its own project name, ports and volumes, migrations applied, dummy accounts and a tiny generated PNG; never reuse a stack that holds real data. Step 1 (SQL only): SHOW CREATE TABLE yearbook_tab to confirm public_id has no explicit collation override. Over a connection using utf8mb4_0900_ai_ci, insert one dummy user_tab row and one yearbook_tab row, then run SELECT id FROM yearbook_tab WHERE owner_id = ? AND public_id = ? with the canonical id, LOWER(canonical) and a variant with one letter accented. Expected if the candidate holds: one row each time. Step 2 (API flow): register a dummy user, create a yearbook, send POST /api/media/create with the yearbook_id field first (lower-cased) and then the file. List the bucket: expect keys under yearbooks/<lower-case>/. Upload a second photo with the canonical id, and add a contributor photo through a note collection link (canonical prefix). POST /api/yearbook/delete with the lower-cased id. Expected: 200, yearbook_tab and media_tab rows gone, bucket still lists the objects (compare with SELECT COUNT(*) and SUM(bytes) on media_tab, which should be 0). Step 3 (control): repeat with a fresh book and delete using the canonical id; expect no objects under yearbooks/<canonical>/. Record only counts and key prefixes, no payloads.

### Owner-observed deployment check
Owner-observed, read-only: list the production bucket under prefix yearbooks/ and flag every second path segment that does not match ^[0-9A-HJKMNP-TV-Z]{26}$ or that has no yearbook_tab row with an exactly equal (BINARY public_id) value. Segments with no row at all are orphans (the documented upload-race orphan can also appear there, so check the spelling pattern first). Also record the bucket's lifecycle rules, versioning, replication and who can read the prefix, to decide whether leftovers are retained and exposed. Send no audit traffic to the deployment; this is an owner-run inventory only.

## 4. Photo download reads each whole object into memory with no concurrency or per-user bound

- Fingerprint: `media/get-content-unbounded-concurrent-object-buffering`
- Affected boundary: Registered account -> API process memory (photo downloads)
- Candidate raised by: `hunt-upload-resource`; independently verified by a fresh verifier who kept it as `needs_validation`.

### Claim
GET /api/media/get-content (any logged-in session, no verified-email requirement) calls Service.Content, which fetches the complete stored object (S3 GetObject followed by io.ReadAll) into a []byte before the handler writes the first response byte, and then hands that slice to http.ServeContent. The slice stays reachable until the client has read the body or the connection's write deadline (2 min route timeout + 10 s slack, set by slowRoute) expires. ETag, If-None-Match, HEAD and Range are evaluated by ServeContent only after the full read, so cheap conditional requests also pay it. The route has RequireUser and slowRoute only: no limiter, semaphore, per-user in-flight cap, connection cap or object-size check (the middleware chain in router.go and the http.Server in server.go add none, and the upload path, by contrast, has an in-flight pool and processing slots). A registered account that owns one stored photo could therefore open many parallel requests for it and read slowly, pinning roughly object size x connections of heap in the shared API process. What source establishes: the per-request whole-object buffering and the absence of any in-process bound on concurrent downloads. What source does not establish: how many connections one client can really hold open through the (not yet written) ALB/WAF, how large the task's memory is, how large the display/print objects can get (display is re-encoded at up to 3000 px as JPEG, or PNG when the image has transparency; the 10 MiB upload cap bounds the source, not the re-encoded output), and whether the edge buffers responses so the task's write completes before a slow client has read. Memory exhaustion of the shared process is therefore unproven and depends on deployment facts.

### Claimed root cause
Service.Content / S3.Get read the entire object into memory for every download request (memory per request equals object size) and nothing in the application bounds concurrent downloads per principal or in aggregate, or checks the known object size (media_tab.bytes) before reading; docs/media.md and docs/container.md size memory for the image-processing path only.

### Source trace
1. `internal/media/handler.go:64` (entrypoint, Handler.Routes): GET /api/media/get-content is registered as h.requireUser(slowRoute(contentRouteTimeout, 0, h.content)): session required, 2 min request deadline, write deadline moved to 2m10s (slowRoute at lines 71-76, constants at lines 33-34); no rate limit, in-flight pool or connection cap.
2. `internal/media/service.go:257` (propagation, Service.Content): After store.owned (owner join, lines 244-247) picks the object key for the requested variant, st.Get(ctx, key) returns the whole object as []byte; the known size m.Bytes is not checked and the handler's conditional/Range logic has not run yet.
3. `internal/storage/s3.go:148` (propagation, S3.Get): io.ReadAll(out.Body) with no size cap, bounded only by the 60 s operation timeout (line 29); storage.go:19-20 documents the assumption that photos are a few MB.
4. `internal/media/handler.go:287` (sink, Handler.content): http.ServeContent(w, r, "", modtime, bytes.NewReader(data)) keeps the whole slice alive while the response is written, until the client has read it or the 2m10s write deadline expires.

### Verified evidence
- `internal/media/handler.go:64`: The download route has no concurrency or rate bound, in contrast to create, which takes an h.inflight slot first (handler.go:100-107) and then the processing slots (service.go:130-136).

## 5. Image limits trust DecodeConfig only, and a decoder panic would leak a processing slot

- Fingerprint: `media/process-header-dims-trust-and-sem-release-without-defer`
- Affected boundary: Uploaded image -> decoder memory and processing slots
- Candidate raised by: `hunt-upload-resource`; independently verified by a fresh verifier who kept it as `needs_validation`.

### Claim
process() checks side, pixel and estimated-memory limits from image.DecodeConfig (image.go:50-51, 185-222) and then calls image.Decode (image.go:54). It never compares the decoded image's Bounds() with the validated config, and it does not check that an NYCbCrA alpha plane covers the luma rectangle. I re-read the Go 1.26 toolchain sources: image/jpeg rejects a second SOF with 'multiple SOF markers' (jpeg/reader.go:302), and image/png parses IHDR only in the dsStart stage, so for JPEG and PNG the header seen by DecodeConfig is the header Decode uses. For WebP the repository imports golang.org/x/image/webp (image.go:15, go.mod:19, v0.46.0). That source is not available offline (no vendor directory, and the local module cache holds only the Go toolchain), so it is unknown whether a VP8X file whose canvas size differs from its VP8/VP8L frame header is rejected by Decode. If it is accepted, a small file declaring a small canvas could pass withinLimits at 2.5 bytes per pixel (image.go:213) while Decode allocates from a larger frame header. It could also yield an *image.NYCbCrA whose alpha plane is shorter than its luma plane. In that case the first panic site would be hasAlpha (image.go:61, 151-154) calling the stdlib (*image.NYCbCrA).Opaque, which slices p.A[i0:i1] (image/ycbcr.go:280-295), or the scaler in resize. Independently, save() takes a processing slot at service.go:131 and releases it with a plain statement at service.go:142 after load() (137) and process() (140). There is no defer, and internal/media has no recover. A panic in a decoder or scaler on the request goroutine would therefore skip the release and leak one of the default 2 slots (SMEM_MEDIA_MAX_CONCURRENT, default 2) until restart. Ordinary error returns do release correctly. I verified that nothing between the handler and save() moves the work to another goroutine: httpx.Timeout (middleware.go:211-219) and httpx.WithTimeout (223-234) call next synchronously, so httpx.Recover (middleware.go:156-178) catches the panic, logs 'panic' with the stack and returns a 500, and the process survives with the slot still held. Both entry paths reach the same save(): the owner upload (POST /api/media/create, handler.go:61 -> Handler.create:112 -> Service.Upload) and the public collection-link submission (POST /api/public-collect/submit-note, notes/handler.go:68 -> submit.go:141 -> notes/service.go:255 -> UploadContributorFrom -> save). The non-deferred release is a confirmed static weakness, but it only matters if some decoder or scaler panic is reachable; that, and the WebP size handling, are unobserved. The unrecovered goroutine at image.go:74 only processes an *image.NRGBA produced by this repository's own resize/orient, so it is hardening and not part of this candidate's exploit path.

### Claimed root cause
Limits are derived from header data (image.DecodeConfig) that the WebP decoder may not use for its allocation, with no post-decode comparison of Bounds() or alpha-plane size against the validated config; and the processing-slot release in save() is not panic-safe (no defer, no recover), so any decoder or scaler panic leaks a slot.

### Source trace
1. `internal/media/handler.go:61` (entrypoint, Handler.Routes (POST /api/media/create)): Authenticated owner upload route (RequireUser plus multipart guard). The public equivalent is POST /api/public-collect/submit-note, registered at internal/notes/handler.go:68 for a link-token holder.
2. `internal/media/handler.go:112` (propagation, Handler.create): readForm buffers the file part (at most SMEM_MEDIA_MAX_BYTES) and hands the bytes to Service.Upload.
3. `internal/notes/service.go:255` (propagation, Service.SubmitNote): Public-link path: each photo loader (submit.go:141 calls SubmitNote on the request goroutine) goes to media UploadContributorFrom, which calls the same save().
4. `internal/media/service.go:131` (propagation, Service.save): A processing slot is taken at 131; load() runs at 137 and process(data) at 140; the slot is released by a plain <-s.sem at 142, not deferred.
5. `internal/media/image.go:50` (propagation, process): image.DecodeConfig supplies the width, height, colour model and format that withinLimits/decodedBytes (lines 51, 185-222) use for every limit.
6. `internal/media/image.go:54` (propagation, process): image.Decode allocates from whatever the decoder itself reads; the result's Bounds() and alpha plane are never compared with cfg before hasAlpha (61) and resize (62).
7. `internal/media/service.go:142` (sink, Service.save): Slot release that is skipped when load() or process() panics.

### Verified evidence
- `internal/media/image.go:50`: Line 49 comment says the dimensions come from the header before any pixel buffer exists; line 50 is the only DecodeConfig call, and nothing after the Decode at line 54 re-checks the decoded bounds.
- `internal/media/image.go:213`: Lossy WebP, including NYCbCrA, is budgeted as px*5/2 bytes from the DecodeConfig size, so the budget is only as correct as that size.

### Exact blockers

It is unknown whether DecodeConfig for a VP8X file returns the canvas size while Decode builds the image from the VP8/VP8L frame header, whether a canvas/frame size mismatch is rejected, and whether the alpha plane is sized from the canvas. This decides whether the limit bypass and the short-alpha-plane panic exist.

## 6. Revoked note-collection links are uncapped, cannot be removed, and get-list returns all of them unpaged

### Claim

## 7. Public-submission slot cap is keyed on the raw client address, and a rate-limited request keeps its slot while its body drains

- Fingerprint: `notes/submit-slot-cap-raw-ip-key-and-drain-on-reject`
- Affected boundary: Anonymous -> 48 shared public-submission slots
- Candidate raised by: `hunt-upload-resource`; independently verified by a fresh verifier who kept it as `needs_validation`.

### Claim
POST /api/public-collect/submit-note takes one of 48 shared slots (SMEM_PUBLIC_UPLOAD_MAX_CONNS) before it reads or authenticates anything, and one client address may hold 8 of them. The address is the string from httpx.ResolveClientIP: the RemoteAddr host, or with SMEM_TRUST_PROXY the last X-Forwarded-For hop that parses as an IP, passed through unmodified. There is no IPv6 prefix grouping, so any six distinct addresses (IPv4, or a few from one IPv6 /64) can reach the 48-slot cap. A slot is held until submit returns. The pace limits (10 s idle, 120 s total, 16 KiB/s average after a 15 s grace) bound the hold to 120 s; a client that declares a large Content-Length, sends about 2 MiB at once and then one byte per under 10 s stays inside them for the full 120 s. An unknown token is answered 404 at once without reading the body, but once an address has used its 60 public_misses hits (or 600 public_all hits) in 15 minutes, Service.Resolve returns a RateLimited error. That error is answered through drainWriter, which reads the rest of the paced body before the first response byte, so the slot is kept for up to 120 s without any valid link token. A holder of a valid token reaches the same hold through the normal spool path, so the drain mainly removes the need for a token. While all 48 slots are held, every other submission gets 503 ERROR_BUSY before its body is read; other routes do not use these slots. ## 8. Public upload spool capacity is not tied to the 48 x 32 MiB admission cap

- Fingerprint: `notes/submit-spool-capacity-not-tied-to-slot-cap`
- Affected boundary: Link-token holder -> upload spool volume / task memory
- Candidate raised by: `hunt-upload-resource`; independently verified by a fresh verifier who kept it as `needs_validation`.

### Claim
A holder of an open collection-link token (no session) can make the API spool up to 32 MiB per request to a temporary file before any content check. Up to 48 requests can be in flight (8 per IP), so the worst case is 1.5 GiB. The code does not relate that figure to the capacity of SMEM_UPLOAD_TMP_DIR. CheckSpool creates and removes one empty file, and config only checks that the directory exists. Source-visible details: (1) Resolve needs only a valid, open link. A valid token refunds the 'misses' limiter (service.go:175), the per-IP and per-collection submission limiters are taken only after the text validates (service.go:236), and the 'all' limiter allows 600 requests per 15 minutes, so oversized garbage bodies are not counted against any of them. (2) The pace limiter does not stop a fast front-load: any rate is allowed during the 15 s grace period, and a body that has already sent about 32 MiB stays far above 16 KiB/s on average for the whole 120 s total (respond.go:73-83). One connection can therefore hold nearly 32 MiB for up to 120 s, and one IP with 8 connections can hold about 256 MiB. (3) When the spool volume is full, the write at submit.go:108 fails and the request is answered 500 (submit.go:113). Every concurrent legitimate submission that needs more space fails the same way until the attacker's connections end. The sizing requirement is written down (docs/media.md:61-62: the volume must exceed 48 x 32 MiB plus headroom) but is not enforced by code. The 64 MiB tmpfs in docs/container.md:21-25 and scripts/image-smoke.sh:243 is a local 'docker run' and smoke-test example, not a production setting. If the spool is memory-backed (tmpfs) and large, the spooled bytes can count toward the container memory limit and add to image-processing memory (about 960 MiB peak per docs/media.md:78). That OOM path depends entirely on the deployed runtime. The repository has no IaC or task definition, so the production volume type, size and memory accounting cannot be read from source.

### Claimed root cause
Admission control counts connections, not bytes. The per-request spool cap (32 MiB) and the slot cap (48 total, 8 per IP) are fixed in code, but the capacity of the spool directory is neither checked at start-up nor reserved per request, so the sizing invariant stated in docs/media.md:61-62 rests on deployment configuration alone.

### Source trace
1. `internal/notes/submit.go:57` (entrypoint, Handler.submit): POST /api/public-collect/submit-note (registered at handler.go:68 with a 32 MiB route body cap). Reachable by any holder of an open link token; there is no session or CSRF layer.

Owner-observed, read-only, no audit traffic sent to the deployment: (1) check the ALB attribute ip-address-type (ipv4 or dualstack), whether the API host name has an AAAA record, and whether CloudFront or any other proxy sits in front of the API; (2) confirm SMEM_TRUST_PROXY and that the task security group accepts the ALB only; (3) read the ElastiCache node type, the parameter group values maxmemory-policy and reserved-memory, and the CloudWatch metrics DatabaseMemoryUsagePercentage and Evictions; (4) during normal load, count keys under smem:<env>:rl:* with SCAN (not KEYS) or compare DBSIZE with the session key count, and note the peak; (5) read the WAF web ACL and ALB rules for rate-based rules and whether they aggregate IPv6 sources by prefix.
