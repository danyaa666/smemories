## 2. Security posture summary

In this partial, source-only pass no unauthenticated cross-tenant read or write, authentication bypass, injection (SQL, DOM, header, template) or code-execution path was found. The authentication, session, owner-scoping and token handling that the hunters traced is carefully built (see section 6). The findings that survived independent verification are mostly **availability and abuse-resistance** weaknesses: one registered account can starve the shared owner-photo-upload pool (the only `confirmed` record, medium), and nine leads depend on production facts the repository does not contain (no infrastructure-as-code exists yet). The most security-relevant lead is a **session-revocation ordering gap** in password reset and the Google pre-hijacking defence; the ordering is visible in source, the exploit window needs a runtime check. Several leads share one root, rate-limit keys built from the raw client-address string, so a single normalisation fix (group IPv6 by prefix) would shrink three of them. Treat the hardening list, above all the `SMEM_ENV` default of `dev`, as a pre-deploy checklist.

## 4. Confirmed finding detail

### Any registered account can hold every owner-upload slot with slow request bodies (medium)

- **Fingerprint:** `media/create-inflight-gate-before-unpaced-body-read`
- **Source location:** internal/media/handler.go:61 -> internal/media/handler.go:208
- **Lower-trust principal:** A free registered user who wants every other owner's photo upload to return 503 ERROR_BUSY.
- **Bounded reproduction (target-native):** 8 concurrent HTTP/1.1 requests: POST /api/media/create with Cookie: smem_session=<the attacker's own session from POST /api/auth/register>, Origin: <an entry of the public allowed-origin list>, Content-Type: multipart/form-data; boundary=B, Content-Length: 10485760; send the opening '--B' line, the part header 'Content-Disposition: form-data; name="file"' and a blank line, then one body byte every ~5 s until the server drops the connection at about 120 s, then reconnect (yearbook_id need not be valid: ownership is checked after the body is read)
- **Conditions:** (authentication_level) Any registered session. Registration is open and e-mail verification is not required for RequireUser; one account is enough because no per-user in-flight cap exists. (system_configuration) Default pool of 4 x SMEM_MEDIA_MAX_CONCURRENT = 8 slots; a larger setting scales the number of connections needed linearly and no source-visible per-client connection limit exists. (network_routing) No front-end control is visible in the repository (no IaC, ALB or WAF source; the deployment is planned, not built). A request-rate rule does not limit 8 long-lived connections; a front end that closes idle connections would end a fully silent body sooner, which a byte-every-few-seconds drip avoids. (timing_dependency) The attacker must reopen the connections about every 2 minutes to keep the pool full; the effect ends within about 2 minutes of the attacker stopping.
- **Actual result:** Source-only result: every condition above is a quoted line; no code was run and no hold time was measured. Nothing between the request line and the blocking body read bounds a slot's hold time other than the single 2 minute absolute read deadline, and nothing counts or limits the concurrent bodies of one user, so 8 stalled or dripping bodies from one session occupy the whole default pool.
- **Impact and priority:** likelihood medium, impact medium, overall medium. While the attack lasts, every owner's photo upload fails with 503 ERROR_BUSY (a core feature, across all tenants). Reads, other APIs, public submissions (separate pool) and stored data are unaffected, nothing persists, and recovery is within about 2 minutes of the attacker stopping. Needs only a free account and 8 long-lived connections re-opened every 2 minutes, with no source-visible per-client connection, pacing or per-user control; but the attacker must sustain it, nothing in the repository shows the product is deployed yet, and edge behaviour is unobserved.
- **Smallest source fix:** Stop letting the client control how long a shared slot is held, and give each account only a share of it. Minimum fix: take a small per-user in-progress cap (for example 2, keyed by u.InternalID) before the global slot, and wrap the body in httpx.PaceBody (idle 10 s, total 2 min, minimum 16 KiB/s after a 15 s grace, as the public route does) so a stalled or dripping body is dropped with 408 within seconds. Do not move the global slot to after the in-memory read: the pool exists to bound request-buffer memory, and acquiring it after io.ReadAll would let many connections each buffer up to 10 MiB without bound. Residual risk of the minimum fix: several accounts could still fill the pool, so the structural fix is to follow internal/notes/submit.go: pace and spool the owner body to a temporary file under its own per-user and global connection caps, and take the memory-bounding slot only when the complete file is loaded for process(), so a slow client costs a socket and some disk, never a shared slot.

Full trace, evidence and fix sketch: see `FINDINGS-DETAIL.md`.

## 6. Hardening notes and positive source patterns

These are not findings. They are hunter observations that no verifier re-checked. The deduplicated full list (75 notes) is in `HARDENING-NOTES.md`.

**Highest-value hardening items**

- `SMEM_ENV` defaults to `dev` and nothing in the repo forces `prod` (`internal/config/config.go:116`, Dockerfile sets no `ENV`). A task that omits it boots with the public OTP key, log mailer (codes printed to stdout), non-`Secure` cookie and no TLS requirements, and `smemories-migrate down --allow-down` would be accepted (`cmd/smemories-migrate/main.go:43`). Three hunters raised it independently. Fix: `ENV SMEM_ENV=prod` in the image or refuse an unset value; owner to confirm the task definition.
- Dev-selected defaults are not registered as dev shortcuts (public `devOTPKey` fallback, log mailer, the four `*_ALLOW_INSECURE` opt-outs), so the planned `scripts/check-no-dev-shortcuts.sh` (not yet present) will not see them.
- `ResolveClientIP` returns raw text: canonicalise with `net.ParseIP(...).String()` and key IPv6 by /64; warn at start-up when `SMEM_TRUST_PROXY` is on and the peer is not private.
- Sessions slide for 30 days with no absolute cap and no per-user session cap; cookies lack the `__Host-` prefix. Add an absolute lifetime and rotate on refresh.
- Account recovery can be denied by anyone who knows an address (3 codes per hour per address, 5 wrong guesses lock the live code). Registration also sends branded mail with an attacker-chosen display name to arbitrary addresses.
- No CSP, HSTS or framing control is set for the SPA host (API-only security headers); the link token also sits in the SPA path `/c/:token`, so edge access logs must not record URLs for `/c/*` and `/api/public-collect/*`.
- Photo quota counts only the display bytes, contributor photos share the owner's 200-photo quota with no per-link cap, and the print-variant goroutine (`internal/media/image.go:74`) has no `recover`.
- Pin the OIDC ID-token algorithm explicitly (`SupportedSigningAlgs: RS256`), refuse a second Google subject for an already linked user, and do not return the email local part as `display_name` to link holders.
- Deletion paths: `DeleteObjects`/`DeleteRows` take raw row ids with no owner parameter, the print key is skipped when `print_key` is empty, and bucket versioning/lifecycle is unknown (hunter-reported gap, deferred).
- CI and tooling: unpinned MinIO and MySQL tags in test infrastructure, Dependabot does not cover `tools/e2e` and `tools/print-check`, `.gitignore` lacks `*.tfstate`, `*.tfvars`, `*.p12`; `tools/e2e/guard.mjs` checks the database name but not the DSN host; the Makefile `include .env` parses `.env` as make syntax.
- `.claude/settings.json` pre-approves `make *`, `go run*`, `npm install*` and `git push*` for agent sessions in this checkout; opening an untrusted branch there would execute contributor-controlled build files without a prompt. `design/canvas/temp*.html` (about 15 MB of bundles) is tracked but unused.

**Positive source patterns the hunters verified (not independently re-verified)**

- Sessions: 256-bit random tokens, only the SHA-256 reaches Redis; login rotates the session; reset and Google-merge purge sessions; a Redis failure answers 503, never anonymous.
- Passwords: Argon2id with bounded stored parameters, a hashing concurrency cap, constant work for unknown accounts, NFKC normalisation.
- Email codes: HMAC at rest, purpose- and user-bound, five attempts counted atomically in one Lua script, single use.
- CSRF: strict Origin allowlist, JSON/multipart Content-Type requirement, SameSite=Lax, no CORS.
- Google OIDC: state, nonce and PKCE bound in an HMAC-signed HttpOnly cookie; `email_verified` must be boolean true; `return_to` validated twice.
- Authorization: every yearbook, media and note query is bound to `owner_id`; foreign and missing ids are indistinguishable; cursors are AES-GCM sealed and scope-bound; the verified-owner flag is re-read from MySQL on every request.
- Link tokens: 192-bit random, SHA-256 stored, shown once, unknown/malformed/revoked answer the same 404; the access log records the route pattern, never the query.
- Injection: all SQL is parameterised (dynamic text is only placeholder lists); no `dangerouslySetInnerHTML`, `innerHTML` or `eval` in the SPA; emails use `html/template`; every stored image is re-encoded and served with the database content type and `nosniff`.
- Configuration and delivery: production refuses plaintext transport, example mail domains and public metrics binds; config errors redact secrets; CI runs on `pull_request` only with `contents: read`, SHA-pinned actions and no secrets; distroless non-root image with an allow-list `.dockerignore`; lockfiles carry integrity hashes and `go.mod` has no `replace`.
